# Poll — очередь сообщений

Всё, что происходит с вашими объектами вне вашего собственного потока команд, доходит до вас
через очередь сообщений, отдельную для каждого регистратора: запрошенный кем-то трансфер, итог
отложенной (`1001`) операции, предупреждение об истечении срока, уведомление об удалении,
событие низкого баланса. Читаете вы её командой EPP `<poll>` (RFC 5730).

У `client.poll` три метода.

| Метод | Что уходит на провод |
|---|---|
| `request()` | `<poll op="req"/>` |
| `ack(messageId)` | `<poll op="ack" msgID="…"/>` |
| `drain(handler, limit = 0)` | цикл `req` / обработка / `ack` поверх обоих |

Каждый возвращает `Promise<Response>`, кроме `drain()`, который разрешается числом обработанных
уведомлений.

**Регулярно разбирайте свою очередь.** Реестр хранит сообщение около месяца; вам ничего не
проталкивается, а очередь, которую никто не читает, — это запрос трансфера, на который никто не
ответил. Во всех примерах ниже предполагается подключённый `client` с выполненным входом — см.
[Быстрый старт](quickstart.md).

---

## request

```js
request()   // => Promise<Response>
```

Запрашивает сообщение в голове очереди. Чтение не удаляет его: то же уведомление придёт снова на
следующем `request()`, пока вы его не подтвердите, поэтому прерванный клиент никогда не теряет
событие.

Здесь важны два кода успеха:

| Код | Значение |
|---|---|
| `1301` | уведомление ожидает, и оно находится в этом ответе |
| `1300` | очередь пуста; ответ не несёт уведомления |

```js
const notice = await client.poll.request();

if (notice.code() === 1300) {
  // Ничего не ожидает.
} else {
  notice.messageId();        // '10021' — идентификатор, который передаётся в ack()
  notice.messageCount();     // 3 — сколько осталось, включая это
  notice.queueMessage();     // 'Transfer requested.' — текст САМОГО УВЕДОМЛЕНИЯ
  notice.queueMessageLang(); // 'uk' | 'ru' | 'en'
  notice.queueDate();        // '2026-08-16T09:15:00Z' — когда поставлено в очередь
}
```

**Читайте уведомление через `queueMessage()`, а не через `message()`.** Это разные элементы.
`message()` возвращает баннер результата команды — «Command completed successfully; ack to
dequeue», — одинаковый в каждом ответе на poll и не говорящий о событии ничего. Цикл, который
читает `message()`, выдаёт вам эту неизменную строку, пока настоящее содержимое остаётся
непрочитанным, а следующий за ним ack уничтожает его в реестре.

`messageCount()` равен `0` на пустой очереди, поэтому он не годится для того, чтобы отличить
«пусто» от «осталось одно»: пользуйтесь кодом.

**Коды ответа:** `1300`, `1301`.

## ack

```js
ack(messageId)   // => Promise<Response>
```

Подтверждает одно уведомление по его идентификатору, что **удаляет его в реестре навсегда**.
Вернуть его нельзя, и повторно оно не доставляется.

```js
const notice = await client.poll.request();

if (notice.messageId() !== null) {
  await store(notice.queueMessage(), notice.pendingActionData());   // СНАЧАЛА обработка
  const after = await client.poll.ack(notice.messageId());          // затем подтверждение
  after.messageCount();   // сколько осталось
}
```

Ответ на ack — это `1301`, пока сообщения остаются (с обновлённым счётчиком, а в этом реестре —
и с идентификатором следующего), либо `1300`, как только очередь опустеет. Тела уведомления он
не несёт никогда; это делает только `req`.

**Старое уведомление всё равно можно подтвердить.** Срок хранения относится к доставке, а не к
вашему подтверждению: как только сообщение вам выдано, оно остаётся подтверждаемым, даже если
месяц истечёт, пока вы его держите. Прочитать, сохранить, подтвердить позже — это поддерживаемый
порядок.

**Коды ответа:** `1300`, `1301`.

## drain

```js
drain(handler, limit = 0)   // => Promise<number>
```

Читает очередь до конца, передавая каждое уведомление вашему обратному вызову и подтверждая его
**после** того, как этот вызов разрешится.

```js
const processed = await client.poll.drain(async (notice) => {
  await store(notice.queueMessage(), notice.pendingActionData());
});
```

`limit`, равный `0`, означает «пока очередь не опустеет». Передайте число, чтобы остановиться
после стольких уведомлений: очередь, которая наполняется быстрее, чем вы её разбираете, иначе
заставит вызов работать бесконечно, а это плохо подходит для всего, что запускается по таймеру.

### Весь смысл — в порядке действий

Подтверждение идёт последним, и ровно ради этого порядка и существует этот помощник.

Подтверждение удаляет уведомление в реестре навсегда. Цикл, который сначала подтверждает, а
обрабатывает вторым шагом, **теряет каждое уведомление, обработка которого сорвалась**: запрос
трансфера, на который вы теперь не можете ответить, итог отложенного создания, который вы теперь
не можете сверить, — и при этом не остаётся ни того, с чего можно повторить, ни записи о том,
что что-то потеряно. Реестр не может прислать уведомление заново, и никакого следа исчезнувшего
не существует.

Поэтому: **если ваш обратный вызов отклонится, уведомление не будет подтверждено.** Оно
останется в голове очереди, а отклонение дойдёт до вас. Устраните причину, разберите очередь
снова — и ничего не потеряно. Следствие сделано намеренно: обратный вызов, который падает
всегда, будет видеть одно и то же уведомление при каждом разборе, потому что альтернатива —
выбросить его.

```js
try {
  await client.poll.drain(async (notice) => {
    await store(notice);           // если это бросит исключение, уведомление останется в очереди
  });
} catch (err) {
  // Очередь цела. Поднимите тревогу, устраните причину, разберите очередь снова.
}
```

### Доставка «хотя бы один раз»

Если сорвётся само подтверждение — соединение оборвётся между разрешением вашего обратного
вызова и доставкой ack, — уведомление останется в очереди, и следующий разбор выдаст его вам
снова. Сделайте обратный вызов идемпотентным и отсеивайте повторы по `messageId()`,
собственному идентификатору этого уведомления в реестре:

```js
await client.poll.drain(async (notice) => {
  const id = notice.messageId();
  if (await alreadyProcessed(id)) return;    // это повторная доставка, а не новое событие
  await store(id, notice.queueMessage(), notice.pendingActionData());
});
```

### Что останавливает цикл

Разбор завершает только `1300`. Пустота никогда не выводится из того, что «ответ не нёс
уведомления», потому что отказ — закрытая сессия, приостановленная учётная запись — выглядит с
этой стороны ровно как разобранная очередь, и цикл отчитался бы об успехе, не прочитав ничего.
Любой другой ответ без уведомления бросается как `CommandError`, построенный по его собственному
коду ответа, поэтому пропавшая сессия доходит до вас ошибкой сессии, а не нулевым счётчиком.

## Что несут уведомления

Кроме текста, большинство уведомлений несут структурированную полезную нагрузку в `<resData>`, и
те же аксессоры, что читают ответ на `info`, читают и её.

| Уведомление | Нагрузка | Чем читать |
|---|---|---|
| Трансфер запрошен / подтверждён / отклонён / отменён | `trnData` | `transfer()`, `transferStatus()`, `objectName()` |
| Домен зарегистрирован, продлён, удалён, восстановлен | `infData` | `objectName()`, `expiryDate()`, `statuses()`, `rgpStatus()` |
| Итог отложенной (`1001`) операции | `panData` | `pendingActionData()` |
| Низкий баланс | `balance:infData` | `balance()`, `currentBalance()` |

### Уведомление о трансфере

То самое, на которое нужно отвечать, а не подшивать. Его получают обе стороны; различается лишь
то, кто из вас может действовать.

```js
await client.poll.drain(async (notice) => {
  const t = notice.transfer();
  if (!t) return;

  // { status: 'pending', requestedBy: 'DELTA', requestedAt: '...',
  //   actingClient: 'EXAMPLE', actBy: '2026-08-21T09:15:00Z', expiryDate: '...' }
  if (t.status === 'pending' && t.actingClient === myClid) {
    // actBy — это крайний срок, и молчание завершает трансфер: после него реестр ПОДТВЕРЖДАЕТ
    // запрос, а не отменяет его.
    await queueForOperatorDecision(notice.objectName(), t.actBy);
  }
});
```

### Уведомление об отложенном действии

Именно так отчитывается отложенная команда. Вы отправляете создание, получаете `1001`
(«принято; результат последует») с `svTRID`, а ответ приходит сюда позже.

```js
const p = notice.pendingActionData();
// { object: 'example.com.ua', success: true,
//   clTRID: 'EXAMPLE-20260816091500-1234-0007',
//   svTRID: 'SRV-20260816091500-24191-00042',
//   date: '2026-08-16T09:20:00Z' }
```

Всё, что вы с ним сделаете, определяют два поля:

- **`success`** — единственное, что говорит, сработала ли операция. Окружающий `1301` означает
  «вот сообщение», а не «ваша операция удалась»; если читать вместо этого код ответа, любой
  ответ на poll будет выглядеть успехом. Отсутствующий вердикт — не вердикт: всё, кроме явного
  «да», возвращается как `false`.
- **`svTRID`** — идентификатор **исходной** команды, а не этого poll. Сопоставьте его с тем,
  который вы сохранили, получив `1001`, чтобы понять, о какой из отложенных операций
  уведомление. Очередь — не стек: не считайте, что речь о самой недавней.

### Уведомление о низком балансе
Тот же элемент, который возвращает [запрос баланса](balance.md), поэтому один парсер обслуживает
оба случая:

```js
const b = notice.balance();
if (b) {
  // { creditLimit: '0.00', balance: '120.00', availableCredit: '120.00' }
  // Деньги — это точная десятичная СТРОКА. Никогда не разбирайте её во float перед сравнением.
}
```

Реагируйте на него. Как только баланс исчерпан, тарифицируемые команды отклоняются с `2104`, и
регистрация, которую вы собирались выполнить, сорвётся из-за нехватки средств, а не из-за чего-то
неправильного в запросе.

### Изменение, которое реестр сделал с вашим объектом (RFC 8590)

Некоторые уведомления описывают то, что произошло с вашим объектом без вашей команды: он перестал
существовать в реестре или ушёл трансфером. Именно на них нужно реагировать автоматически —
прекратить тарификацию, сообщить клиенту, убрать из своего учёта, — а предложение в `<msg>`
написано на языке уведомлений вашей учётной записи, поэтому разбирать его ненадёжно.

```js
const chg = notice.change();
if (chg) {
  chg.operation;       // 'delete' | 'transfer' | 'renew' | 'update' | 'restore' | 'autoRenew' | …
  chg.state;           // 'before' | 'after'
  chg.who;             // 'Registry'
  chg.date;
  chg.svTRID;
  chg.reason;
  notice.objectName();
}
```

**`state` говорит, как читать объект рядом.** `after` описывает объект таким, каков он сейчас.
`before` — таким, каким он был в последний раз; домен, которого уже нет, иначе и не описать.
Записать блок `before` в своё хранилище как *текущее* состояние — это ровно то, как удалённый домен
оживает в ваших записях, поэтому ветвитесь по этому полю до сохранения.

`change()` не возвращает ничего, когда уведомление не несёт блока изменения, — а это каждое
уведомление, если вы не объявили `urn:ietf:params:xml:ns:changePoll-1.0` при входе. Эта библиотека
зеркалит greeting сервера в `<svcs>`, поэтому реестр, который его предлагает, объявляется за вас.

В отличие от правила о переносе, отсутствие объявлений **не** даёт вам `changeData`: реестр
отправляет его только клиенту, который назвал пространство имён, потому что клиент, никогда его не
видевший, может отвергнуть весь кадр. Предложение `<msg>` не меняется в обоих случаях, поэтому
объявление никогда не забирает то, что вы уже читаете.

## Когда полезная нагрузка приходит перенесённой (RFC 9038)

Уведомление попадает в вашу очередь раньше, чем реестр узнаёт, какая сессия его заберёт, поэтому
оно может содержать элемент из пространства имён расширения. Если ваш вход объявил список
расширений и этого пространства имён среди них не было, реестр не кладёт элемент в `<resData>` —
вместо этого он переносит его в `<extValue>` внутри `<result>`, с причиной, называющей
пространство имён, которое вам нужно было бы объявить.

По умолчанию эта библиотека входит, объявляя ровно те расширения, которые предложило приветствие
сервера, поэтому вы получаете типизированную форму. С перенесённой формой вы встретитесь, только
если сузите `extUris` в [конфигурации](session.md).

Так или иначе, кадр остаётся валидным, данные остаются в нём, а уведомление остаётся
подтверждаемым — ничто не теряется молча:

```js
for (const ext of notice.extValues()) {
  ext.element;     // 'infData'
  ext.namespace;   // URI, который не был объявлен
  ext.values;      // дочерние элементы по именам: { balance: '120.00' }
  ext.xml;         // элемент в том виде, в каком он пришёл, чтобы разобрать его самостоятельно
  ext.reason;      // почему он был перенесён
}
```

Всегда подтверждайте такое уведомление через `ack`, как и любое другое. Оставив его лежать
только потому, что оно выглядит незнакомым, вы заклините очередь за ним.

## Полный разбор очереди, от начала до конца

```js
const { Client, Config, EppError } = require('@epptools/sdk');

const client = new Client(new Config({
  host: 'epp.registry.example',
  clid: 'EXAMPLE',
  password: 'your-secret',
  caFile: '/path/to/registry-ca.pem',
}));

try {
  await client.connect();
  await client.login();

  const processed = await client.poll.drain(async (notice) => {
    const id = notice.messageId();
    if (await alreadyProcessed(id)) return;

    await store({
      id,
      queuedAt: notice.queueDate(),          // собственная строка реестра
      text: notice.queueMessage(),
      lang: notice.queueMessageLang(),
      object: notice.objectName(),
      transfer: notice.transfer(),
      pending: notice.pendingActionData(),
    });
  });

  console.log(`${processed} notices processed`);
  await client.logout();
} catch (err) {
  if (err instanceof EppError) console.error(err.message);
} finally {
  client.disconnect();
}
```
