# Ответы

Каждая команда разрешается объектом `Response` — разобранным ответом, у которого есть именованный
аксессор для всего, что реестр может прислать. Вам не нужно ни лезть в разобранный документ по
угаданной строке, ни трогать XML, если вы сами того не захотите.

Поиск элементов идёт по **локальному имени и URI пространства имён**, никогда по префиксу, поэтому
реестр, который пишет префиксы иначе, не ломает ни одного аксессора с этой страницы.

Два правила действуют повсюду, и именно их нарушение стоит денег:

- **Даты — это собственная строка реестра**, `2027-04-01T09:15:00Z`, а не `Date`. Именно реестр
  решает, на какой календарный день попадёт продление; переформатирование через местный часовой пояс
  — это то, из-за чего клиент в итоге показывает и продлевает по вчерашнему дню.
- **Деньги — это точная десятичная строка**, `'100.00'`, а не число. В двоичной плавающей точке
  `0.1 + 0.2` не равно `0.3`, и просуммированный так баланс уплывает. Пользуйтесь библиотекой
  десятичной арифметики или целыми числами в младших единицах валюты.

## Результат

| Аксессор | Что возвращает | Когда в ответе ничего нет |
|---|---|---|
| `code()` | код ответа EPP числом: 1000, 1001, 2303 … | `0` — такого кода в EPP не бывает, поэтому он означает «в этом кадре результата не было», например у приветствия |
| `isSuccess()` | `true` для любого кода от 1000 до 1999 | `false` |
| `isPending()` | `true` ровно для 1001 | `false` |
| `isGreeting()` | `true`, когда кадр — это `<greeting>`, а не `<response>` | `false` |
| `message()` | понятный человеку текст `<result><msg>` | `null` |
| `messageLang()` | язык этого текста: `'en'`, `'uk'`, `'ua'` или `'ru'` | `null` |
| `statuses()` | значения статусов объекта, например `['ok']` или `['clientHold', 'clientUpdateProhibited']` | `[]` |
| `errorReasons()` | дополнительный текст `<reason>`, который реестр приложил к отказу | `[]` |
| `extValues()` | блоки `<extValue>` целиком — см. ниже | `[]` |
| `clTRID()` | идентификатор транзакции, отправленный вашей командой и возвращённый в ответе | `null` |
| `svTRID()` | собственный идентификатор транзакции реестра | `null` |

```js
const r = await client.domain.info('example.com.ua');
r.code();        // 1000
r.statuses();    // ['ok']
r.svTRID();      // сохраните это рядом с доменом
```

### `extValues()`

```js
r.extValues();
// [{ element, namespace, text, values, xml, reason, lang }, …]
```

`errorReasons()` даёт один лишь текст, с которым ничего не сделаешь: он говорит, что что-то
отклонено, но никогда — какое из пяти отправленных вами имён. `extValues()` говорит какое. Так EPP
указывает на проблемную часть запроса, и каждая запись несёт:

| Поле | Что в нём |
|---|---|
| `element` | локальное имя элемента, к которому у реестра претензия, например `name` |
| `namespace` | URI пространства имён этого элемента или `''` |
| `text` | его символьные данные — для обычного случая, листа вроде `<domain:name>bad..name</domain:name>`, это и есть ответ |
| `values` | его дочерние элементы по локальному имени — на случай, когда элемент не лист, а контейнер |
| `xml` | элемент, сериализованный обратно в том виде, в каком пришёл, если вы предпочитаете разобрать его сами |
| `reason` | текст `<reason>` рядом с ним |
| `lang` | язык этого текста |

У контейнера `text` приходит пустым, потому что собственных символьных данных у контейнера нет, —
для этого и есть `values` и `xml`. Сервер может также перенести в этот блок данные, которые не смог
вернуть обычным способом (RFC 9038); содержимое `<value>` отдаётся как данные и никогда не
интерпретируется.

## Идентичность объекта

На эти вопросы отвечает любой объект — домен, хост или контакт.

| Аксессор | Что возвращает | Когда в ответе ничего нет |
|---|---|---|
| `objectName()` | имя домена, имя хоста или **идентификатор** контакта | `null` |
| `roid()` | собственный идентификатор объекта в реестре | `null` |
| `sponsor()` | `clID` регистратора, которому объект принадлежит сейчас | `null` |
| `registrarOfRecord()` | идентификатор, который WHOIS и RDAP реестра публикуют как регистратора | `null` |
| `createdBy()` | `crID` — кто создал | `null` |
| `createdDate()` | `crDate`, собственной строкой реестра | `null` |
| `updatedBy()` | `upID` — кто изменил последним | `null`, если объект ни разу не менялся |
| `updatedDate()` | `upDate` | `null`, если объект ни разу не менялся |
| `authInfo()` | код авторизации трансфера объекта, `<authInfo><pw>` | `null`, если реестр его не отдал |

`objectName()` читает непосредственного потомка блока объекта, и на контакте это важно: поиск
элемента `<name>` по всему документу нашёл бы сначала полное имя человека внутри почтового блока, а
подстановка его обратно как идентификатора зарабатывает 2303. При `contact.createAuto()` именно
здесь появляется выданный реестром идентификатор — и больше нигде, так что сохраните его.

`sponsor()` и `registrarOfRecord()` — не одно и то же лицо. `sponsor()` называет учётную запись,
которой принадлежит объект, — в вашей собственной реселлерской иерархии это вы; `registrarOfRecord()`
— то, что реестр публикует для всего мира, а для реселлера это кто-то другой.

`updatedBy()` вместе с `updatedDate()` — это то, по чему вы сверяетесь: изменение, которого вы не
делали, пришло со стороны реестра или от действия поддержки, а не из вашей системы.

**`authInfo()` — это действующие учётные данные.** Он присутствует только у регистратора-владельца и
только в том `info`, который его запросил. Кто им владеет, тот может увести домен к другому
регистратору. Никогда не пишите его в журнал, никогда не вкладывайте в обращение в поддержку и
меняйте его после того, как передали клиенту.

## Домен

| Аксессор | Что возвращает | Когда в ответе ничего нет |
|---|---|---|
| `expiryDate()` | `exDate` ровно в том виде, в каком его написал реестр | `null` |
| `registrant()` | идентификатор контакта-регистранта | `null` |
| `contacts()` | контакты ролей по ролям: `{ admin: ['c-1'], tech: ['c-1', 'c-2'] }` | `{}` |
| `contactsFor(role)` | идентификаторы в одной роли, сопоставление без учёта регистра | `[]` |
| `adminContacts()` | административные контакты | `[]` |
| `techContacts()` | технические контакты | `[]` |
| `billingContacts()` | биллинговые контакты | `[]` |
| `allContacts()` | каждый идентификатор, привязанный в любом качестве, включая регистранта, без повторов | `[]` |
| `nameservers()` | делегирование, именами в нижнем регистре | `[]` |
| `nameserverAddresses()` | встроенные glue-адреса по имени сервера имён | `{}` |
| `subordinateHosts()` | объекты хостов, живущие **под** этим доменом | `[]` |
| `transfer()` | трансфер целиком — см. ниже | `null` |
| `transferStatus()` | `trStatus`, например `'pending'` или `'serverApproved'` | `null` |
| `transferDate()` | когда объект последний раз менял владельца | `null`, если не менял ни разу |
| `rgpStatus()` | статусы выкупа, например `['redemptionPeriod']` (RFC 3915) | `[]` |
| `license()` | номер товарного знака или лицензии из собственного расширения реестра | `null` |
| `dsRecords()` | DS-записи DNSSEC (RFC 5910) | `[]` |
| `keyRecords()` | записи ключей DNSSEC | `[]` |
| `isSigned()` | `true`, когда есть хоть одна DS-запись или запись ключа | `false` |
| `prices()` | подсказки о цене продления и восстановления, по операциям | `{}` |
| `priceChannel()` | непрозрачный идентификатор строки каталога цен, по которой тарифицируется этот домен | `null` |

`contacts()` намеренно не включает регистранта: это отдельный элемент со своим смыслом, читайте его
через `registrant()`. `contactsFor()` сопоставляет роль без учёта регистра, потому что реестры
непоследовательны в `tech` против `Tech`, а точное сравнение сообщит «технического контакта нет» о
домене, у которого он есть. Пустой список — законный ответ: обязателен везде только регистрант.

`nameservers()` возвращает имена в том виде, в каком их выразил реестр, — хоть как
`<domain:hostObj>` (ссылка на объект хоста), хоть как `<domain:hostAttr>` (имя со встроенными
glue-адресами). Чтение только одной из двух моделей даёт пустой список против реестра, который
использует другую, а это читается как «у домена нет серверов имён». `nameserverAddresses()`
заполняется только для встроенной модели:

```js
r.nameservers();
// ['ns1.example.com.ua', 'ns2.example.com.ua']

r.nameserverAddresses();
// { 'ns1.example.com.ua': [{ ip: '203.0.113.1', version: 'v4' },
//                          { ip: '2001:db8::1',  version: 'v6' }] }
```

Пустой результат `nameserverAddresses()` **не** означает, что домен не делегирован. Против реестра,
который отвечает ссылками на объекты хостов, имена вы получаете здесь, а адреса добираете вызовом
`host.info()` на каждое имя.

`subordinateHosts()` важен перед удалением: реестр отказывается удалять домен, пока под ним живут
объекты серверов имён. Сначала посмотрите список и удалите их или перенаправьте.

```js
r.transfer();
// { status: 'pending',
//   requestedBy: 'ACME', requestedAt: '2026-08-10T09:00:00Z',
//   actingClient: 'EXAMPLE', actBy: '2026-08-15T09:00:00Z',
//   expiryDate: '2028-01-15T00:00:00Z' }
```

Один только `transferStatus()` говорит, что трансфер в ожидании, но не говорит, чей он и сколько у
вас времени. `actBy` — это срок, после которого реестр решит за вас.

```js
r.dsRecords();   // [{ keyTag: 12345, alg: 8, digestType: 2, digest: 'ABCD…' }]
r.keyRecords();  // [{ flags: 257, protocol: 3, alg: 8, pubKey: 'AwEAA…' }]
```

`prices()` возвращает `{ renewal: { value: '90.00', currency: 'UAH' }, … }` — подсказки реестра о
цене в ответе на `info`, по операциям. За котировкой, на которую можно опереться до покупки,
обращайтесь запросом цены в `domain.check()` и читайте [`fees()`](#check-и-деньги).
`priceChannel()` привязан к домену, а не к зоне: домен, зарегистрированный давно, может стоять на
другой строке каталога, чем та, по которой пошла бы новая регистрация в той же зоне.

## Хост

| Аксессор | Что возвращает | Когда в ответе ничего нет |
|---|---|---|
| `hostAddresses()` | glue-адреса хоста: `[{ ip: '203.0.113.10', version: 'v4' }, …]` | `[]` |

Glue-адреса несёт только хост **внутри** зоны, которую он обслуживает. Для внешнего сервера имён
реестр не возвращает ни одного, и это норма, а не потерянный ответ. Отсутствующий атрибут версии
читается как `v4` — таково значение по умолчанию в самой схеме хоста.

Этот аксессор относится к самому объекту хоста. Встроенные glue-адреса домена — это
`nameserverAddresses()`, который держит каждый адрес рядом с тем сервером имён, которому он
принадлежит.

## Контакт

| Аксессор | Что возвращает | Когда в ответе ничего нет |
|---|---|---|
| `postalInfo()` | почтовые адреса по формам: `int` и `loc` | `{}` |
| `email()` | адрес электронной почты контакта | `null` |
| `voice()` | номер телефона в форме EPP `+CC.NNNNNNNNN` | `null` |
| `fax()` | номер факса, в той же форме | `null` |
| `disclose()` | предпочтение раскрытия — см. ниже | `null`, когда контакт его не несёт и действует одна лишь политика реестра |

```js
r.postalInfo();
// { int: { name: 'ACME LLC', org: '', street: ['1 Example St'],
//          city: 'Kyiv', sp: '', pc: '01001', cc: 'UA' },
//   loc: { name: 'ТОВ АКМЕ',  org: '', street: ['вул. Прикладна, 1'],
//          city: 'Київ', sp: '', pc: '01001', cc: 'UA' } }
```

`int` — форма в ASCII, которую принимает любой реестр и которая переживает печать, отправку почтой и
чтение системой, не знающей кириллицы. `loc` — местное письмо, адрес в том виде, как его написал сам
регистрант. Контакт может нести любую из форм или обе, а части, которых реестр не прислал,
возвращаются как `''`, а не отсутствуют, поэтому читать их можно без проверки на каждом обращении.

```js
r.disclose();
// { flag: false, elements: ['email', 'voice', 'name:int'] }
```

`flag` — это весь смысл списка: `true` означает, что перечисленные элементы **можно** публиковать,
`false` — что их следует скрывать. Элементы, которых в списке нет, получают противоположное флагу,
поэтому чтение списка без флага выворачивает настройку приватности наизнанку. Поля, существующие по
одному на каждую почтовую форму, обозначаются как `name:int`, `addr:loc` и так далее.

## Check и деньги

| Аксессор | Что возвращает | Когда в ответе ничего нет |
|---|---|---|
| `availability()` | весь ответ check целиком: `{ 'example.com.ua': true, 'taken.com.ua': false }` | `{}` |
| `isAvailable(name)` | `true` или `false` для одного имени, сопоставление без учёта регистра | **`null`** — в ответе о нём не сказано ничего |
| `unavailableReason(name)` | почему имя недоступно, например `'In use'` или `'Reserved'` | `null`, когда имя доступно или реестр не назвал причины |
| `fees()` | таблица цен RFC 8748 по именам — см. ниже | `{}` |
| `feeFor(name, operation, years = 1)` | одна котировка, точной десятичной строкой | `null` |
| `feeClass(name)` | тарифный класс реестра, например `'premium'` или `'standard'` | `null` |
| `isPremium(name)` | `true`, когда имя тарифицируется вне обычного прайс-листа | `false` |
| `chargedFee()` | сколько изменяющая команда списала на самом деле: `{ currency: 'UAH', fee: '100.00' }` | `null` |
| `feeAmount()` | только сумма из этого | `null` |
| `feeCurrency()` | только валюта из этого | `null` |
| `balance()` | блок учётной записи: `{ creditLimit, balance, availableCredit }` | `null`, когда ответ не является ответом о балансе |
| `creditLimit()` | ваша кредитная линия | `null` |
| `currentBalance()` | ваш текущий баланс | `null` |
| `availableCredit()` | сколько ещё можно потратить: баланс плюс кредитная линия, если она есть | `null` |

**`isAvailable()` возвращает три значения, а не два.** `null` означает, что вердикта об этом имени в
ответе не было вовсе, а это не то же самое, что «занято», и не должно выглядеть так же для строки,
которая имя регистрирует. Сравнивайте с `true` явно:

```js
if (check.isAvailable(name) !== true) return;    // покрывает и false, И null
```

```js
const r = await client.domain.check(['example.com.ua'], { create: [1, 2, 5] }, 'UAH');

r.fees();
// { _currency: 'UAH',
//   'example.com.ua': {
//     avail: true,
//     reason: null,
//     class: 'premium',                      // есть, только если реестр его назвал
//     commands: { create: { years: 1, fee: '100.00' } },
//     periods: [ { op: 'create', years: 1, fee: '100.00' },
//                { op: 'create', years: 2, fee: '195.00' },
//                { op: 'create', years: 5, fee: '480.00' } ] } }

r.feeFor('example.com.ua', 'create', 5);   // '480.00'
```

`_currency` — валюта, в которой котирована вся таблица. По каждому имени `avail: false` вместе с
`reason` — это способ реестра сказать, что он не может назначить цену этому имени (необслуживаемая
зона или валюта, в которой он не котирует), и это ответ, отдельный от недоступности самого имени.

В `commands` по одной записи на операцию, а в `periods` — все котировки. Запрос одной операции на
несколько сроков возвращает несколько котировок с одинаковым именем операции, поэтому за конкретной
цифрой обращайтесь к `feeFor()`, а не индексируйте `commands`. `transfer` и `restore` — операции на
один год, сколько бы лет вы ни спросили; читайте их обратно на 1.

`false` из `isPremium()` — не обещание обычной цены, а лишь то, что в ответе не объявлен особый
класс. Считайте деньги по `fees()` и повторяйте цену в самой изменяющей команде, чтобы реестр мог
отказать, а не списать лишнее. Суммы здесь приведены для примера и не являются тарифом реестра.

`chargedFee()`, `feeAmount()` и `feeCurrency()` читают отражённое значение в удавшейся изменяющей
команде, которая несла согласование цены, — сумму, которую с вас действительно списали. Сверяться
нужно с ней, а не с той, которую вы котировали.

Аксессоры баланса работают с ответом на `client.balance()`; все три величины — точные десятичные
строки. См. [Баланс](balance.md).

## Poll

| Аксессор | Что возвращает | Когда в ответе ничего нет |
|---|---|---|
| `messageId()` | идентификатор, который передаётся в `poll.ack()` | `null` — в этом ответе уведомления нет |
| `messageCount()` | сколько уведомлений остаётся в очереди | `0` |
| `queueMessage()` | **текст уведомления**, из `<msgQ><msg>` | `null` |
| `queueMessageLang()` | язык этого уведомления: `'uk'`, `'ru'` или `'en'` | `null` |
| `queueDate()` | когда уведомление поставили в очередь | `null` |
| `pendingActionData()` | итог операции, выполненной офлайн, — см. ниже | `null` |

`queueMessage()` — это **не** `message()`. `message()` возвращает баннер результата команды
(«Command completed successfully; ack to dequeue»), одинаковый в каждом ответе poll. Чтение
уведомления через `message()` отдаёт вам эту постоянную строку, а настоящее содержимое пропадает — и
подтверждение затем уничтожает его в реестре навсегда.

```js
r.pendingActionData();
// { object: 'example.com.ua',
//   success: true,
//   clTRID: 'NODEJS-SDK-20260816103012-24191-0003',
//   svTRID: 'SRV-19700101103512-24191-00007',
//   date:   '2026-08-16T10:31:00Z' }
```

Так отчитывается отложенная команда (RFC 5731 §3.3, RFC 5733 §3.3). Вы отправляете create, получаете
1001 с `svTRID`, а ответ приходит позже в очередь. Три вещи о его чтении:

- **Только `success` говорит, сработало ли.** Окружающий код ответа 1301 означает «вот сообщение», а
  не «ваша операция удалась». Если читать вместо него код ответа, любой ответ poll будет выглядеть
  как успех.
- **`svTRID` — это идентификатор исходной команды**, а не этого ответа poll. Сопоставьте его с тем,
  который вы сохранили при 1001, чтобы понять, о какой ожидающей операции речь. Poll — это очередь;
  уведомление в её начале не обязательно о самом недавнем вашем действии.
- `date` — когда действие завершилось, а не когда вы опросили очередь.

Полный цикл, включая то, почему подтверждение должно идти после вашей обработки, а не до неё, — в
[Poll](poll.md).

## Безопасность сессии и приветствие

| Аксессор | Что возвращает | Когда в ответе ничего нет |
|---|---|---|
| `securityEvents()` | предупреждения RFC 8807 об этой сессии | `[]` — сессия здорова |
| `serviceObjUris()` | объектные пространства имён, которые объявляет приветствие | `[]` |
| `serviceExtUris()` | пространства имён расширений, которые объявляет приветствие | `[]` |

```js
for (const event of (await client.login()).securityEvents()) {
  // { type, level, text, name?, exDate?, value?, duration?, lang? }
  alert(event.level, event.type, event.text, event.exDate);
}
```

`type` — это одно из `password`, `certificate`, `cipher`, `tlsProtocol`, `newPW`, `stat` или
`custom`; `level` — `'warning'` или `'error'`. Поскольку на здоровой сессии список пуст, любая
запись — повод что-то сделать: сертификат, истекающий через три недели, приходит сюда как
`type: 'certificate'` с датой в `exDate`. См. [Сессию](session.md#безопасность-входа-rfc-8807).

Два аксессора сервисов читают приветствие — то самое, которым разрешаются `connect()` и `hello()`.

## Прямой доступ

| Аксессор | Что возвращает | Когда в ответе ничего нет |
|---|---|---|
| `value(local)` | первый элемент с таким локальным именем где угодно в кадре, с обрезанными пробелами | `null` |
| `values(local)` | все элементы с таким локальным именем, с обрезанными пробелами | `[]` |
| `resData()` | элемент `<resData>` разобранного дерева | `null` |
| `root()` | корень разобранного дерева | у разобранного кадра корень есть всегда |
| `raw()` | XML ответа ровно в том виде, в каком он пришёл | кадр как прочитан |
| `Response.fromXml(xml)` | разбирает кадр в `Response` (статический) | бросает `ConnectionError` на всём, что не является одним корректно сформированным деревом элементов |

```js
r.value('exDate');     // элемент, который не покрыт именованными аксессорами
r.values('hostObj');   // все такие элементы
```

Это запасной выход для расширения, аксессора для которого в библиотеке нет, и способ прочитать
[произвольный кадр](commands.md#произвольные-кадры), собранный вами самими. Оба сопоставляют по
локальному имени и игнорируют пространства имён, поэтому `value('name')` находит первый `<name>` в
порядке документа, какой бы префикс у него ни был. Там, где именованный аксессор существует,
пользуйтесь им: он знает, *какой* элемент ему нужен.

`Response.fromXml()` отвергает усечённый кадр, а не возвращает частичное дерево, — и именно это не
даёт наполовину доставленному create прочитаться как завершённая и оплаченная регистрация.
