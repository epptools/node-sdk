# Сессия

Сессия EPP — это TLS-сокет к реестру на порту 700, `<greeting>`, которое сервер отправляет первым,
`<login>`, несколько команд и `<logout>`. Эта страница описывает всё перечисленное: настройки,
которыми открывается сокет, проверки сертификата, четыре команды сессии, смену пароля, блок
безопасности RFC 8807 и то, как журналировать кадры, не журналируя учётные данные.

## Config

`Config` хранит настройки соединения. Создайте его один раз и передайте в `Client`; менять его потом
не предполагается.

```js
const { Client, Config } = require('@epptools/sdk');

const client = new Client(new Config({
  host: 'epp.registry.example',
  port: 700,
  clid: 'EXAMPLE',
  password: process.env.EPP_PASSWORD,
  caFile: '/etc/epp/registry-ca.pem',
  lang: 'uk',
  connectTimeout: 10000,
  readTimeout: 30000,
}));
```

| Поле | По умолчанию | Что это |
|---|---|---|
| `host` | `''` | имя хоста реестра |
| `port` | `700` | порт EPP |
| `clid` | `''` | ваш идентификатор регистратора |
| `password` | `''` | ваш пароль EPP |
| `lang` | `'en'` | язык сообщений реестра о результате |
| `connectTimeout` | `10000` | срок на рукопожатие TLS, **в миллисекундах** |
| `readTimeout` | `30000` | срок на каждый ответ, **в миллисекундах** |
| `verifyPeer` | `true` | проверять сертификат сервера по `caFile` или системному хранилищу |
| `verifyPeerName` | `true` | требовать, чтобы сертификат совпадал с `host` |
| `caFile` | `null` | путь к PEM со связкой CA, которой подписан **серверный** сертификат |
| `clientCert` | `null` | путь к PEM вашего клиентского сертификата — для точки подключения со взаимным TLS |
| `clientKey` | `null` | путь к PEM соответствующего закрытого ключа |
| `clientKeyPassphrase` | `null` | пароль к этому ключу, если он зашифрован |
| `objUris` | `null` | объектные сервисы, объявляемые при входе; `null` означает «те, что предложило приветствие» |
| `extUris` | `null` | сервисы расширений, объявляемые при входе; `null` означает то же самое |
| `clTRIDPrefix` | `'NODEJS-SDK'` | префикс генерируемых клиентских идентификаторов транзакций |
| `registryExtUri` | `null` | пространство имён СОБСТВЕННОГО объектного расширения этого реестра; `null` читает его из приветствия. Задавайте вручную только для реестра, чьё расширение названо не по образцу `…/registry-<версия>`. Неверное значение сервер не отвергает, а игнорирует, поэтому данные молча не доходят. См. [Команды](commands.md#собственные-расширения-вашего-реестра). |
| `registryBalanceUri` | `null` | то же самое для расширения баланса учётной записи |
| `loginSecurity` | `true` | участвовать в расширении Login Security (RFC 8807) там, где сервер его предлагает |

### Что происходит при неверном значении поля

**`host`** — пустой хост ловит `connect()`: он бросает `ConfigError: Config: host must not be empty`
раньше, чем будет открыт хоть один сокет. Хост, который не разрешается в адрес или отказывает в
соединении, выходит из `connect()` как `ConnectionError` с указанием адреса.

**`port`** — любой порт, кроме EPP-порта на этом хосте, либо откажет в соединении, либо провалит
рукопожатие TLS. Библиотека говорит только на EPP поверх TLS: режима без шифрования нет, отката тоже
нет.

**`clid`, `password`** — оба проверяются в `login()` ещё до сборки кадра. Пустое значение любого из
них — это `ConfigError` с указанием, какое именно. Неверные учётные данные — совсем другое дело: это
отказ со стороны сервера, код ответа 2200, поднимаемый как `AuthError`.

**длина `password`** — схемный тип `<pw>` из RFC 5730 допускает от 6 до 16 символов. Пароль вне
диапазона 6–128 — это `ConfigError` ещё до подключения. От 17 до 128 символов он может ехать только
внутри блока RFC 8807, поэтому, если приветствие сервера этого расширения не объявляет, вы получите
`ConfigError` ровно об этом, а не голый 2001, которым ответил бы сервер и который не называет ни
одного поля.

**`lang`** — должен быть одним из объявленных сервером (`en`, `uk`, `ua`, `ru`; `ua` и `uk` — оба
украинский). Всё прочее отклоняется при входе кодом 2102 и поднимается как `CommandError`. Язык
влияет на текст `<msg>` от реестра и больше ни на что: коды ответа одинаковы на всех языках.

**`connectTimeout`, `readTimeout`** — миллисекунды, минимум 1000, проверяются при создании `Config`.
Значение, которое не является положительным числом или меньше 1000, немедленно бросает `ConfigError`
с сообщением, подсказывающим эквивалент в миллисекундах. Оно отклоняется, а не поднимается молча до
нижней границы, потому что `readTimeout: 30`, прочитанный как миллисекунды, — это тридцатая доля
секунды: такой короткий срок на create или renew истечёт, пока реестр ещё работает, команда вполне
могла быть выполнена и оплачена, а тайм-аут чтения необратим — и клиент сообщил бы об ошибке для
операции, которая на самом деле удалась.

**`caFile`, `clientCert`, `clientKey`** — читаются с диска в момент вызова `connect()`.
Несуществующий путь роняет подключение файловой ошибкой (`ENOENT`) ещё до открытия сокета. Это
проблема развёртывания, а не протокола, и она намеренно не маскируется под `ConnectionError`.

**`objUris`, `extUris`** — оставьте оба `null`. Тогда клиент объявляет ровно то, что предложило
приветствие, и сессию никогда не отклонят с кодом 2307 за запрос сервиса, которого у сервера нет.
Задавайте их, только чтобы *сузить* объявляемое. Пустой массив не объявляет в этой категории ничего,
то есть выключает соответствующие расширения на всю сессию; базовый URI `epp-1.0` никогда не
отправляется как объектный сервис, потому что он им не является. Если приветствие не перечислило ни
одного сервиса, клиент откатывается к стандартным объектным отображениям RFC и к расширениям,
которые публикует этот реестр.

**`clTRIDPrefix`** — стоит в начале каждого сгенерированного клиентского идентификатора транзакции,
чтобы ваши команды находились в общем журнале. См.
[Команды](commands.md#клиентские-идентификаторы-транзакций).

**`loginSecurity`** — присвойте ровно `false`, чтобы не участвовать в расширении. Чем вы при этом
жертвуете — в разделе [Безопасность входа](#безопасность-входа-rfc-8807).

## TLS

| Ситуация | Настройка |
|---|---|
| `epp.registry.example:700` (сертификат частного CA) | задайте `caFile` на `.pem` с CA реестра — **обязательно** |
| Публичный сертификат, которому доверяет браузер | значения по умолчанию (`verifyPeer: true`, `verifyPeerName: true`) |
| Несовпадение имени хоста при разработке | `verifyPeerName: false` |
| Точка подключения со взаимным TLS | `clientCert` + `clientKey` (+ `clientKeyPassphrase`, если ключ зашифрован) |

Публичная точка подключения `epp.registry.example:700` предъявляет сертификат, выпущенный **собственным
частным CA** реестра, поэтому `caFile` должен указывать на связку с этим CA: в системном хранилище
доверия его нет, и без него рукопожатие не проходит. Точка подключения — строгий EPP по RFC, и
клиентский сертификат ей **не нужен**: аутентификация — это clID и пароль поверх TLS плюс список
разрешённых IP-адресов в вашей учётной записи.

Соединение согласует TLS не ниже 1.2, отправляет заданный `host` как имя сервера в SNI и проверяет
цепочку сертификатов, если вы это не отключили.

### Когда рукопожатие не проходит

Самый частый сбой при первом запуске — проверка сертификата, и выглядит он так:

```
ConnectionError: TLS/socket error on epp.registry.example:700 — certificate verify failed
```

Почти всегда это значит, что `caFile` не задан или указывает не на ту связку. Проверьте его прежде
всего:

```bash
openssl s_client -connect epp.registry.example:700 -CAfile /path/to/registry-ca.pem </dev/null
# "Verify return code: 0 (ok)" означает, что связка верная; всё остальное — что нет.
```

Другие сбои рукопожатия и что они значат:

| Сообщение | Причина |
|---|---|
| `certificate verify failed` | неверный или отсутствующий `caFile` |
| `Hostname/IP does not match certificate's altnames` | сертификат тот, но выпущен на другое имя — проверьте `host`, прежде чем хвататься за `verifyPeerName: false` |
| `Connect to epp.registry.example:700 timed out after 10000 ms` | никто не ответил: межсетевой экран, неверный порт или вашему IP закрыт доступ к точке подключения |
| `ECONNREFUSED` | по адресу что-то ответило, но на этом порту никто не слушает |
| `ENOENT` при подключении | `caFile` / `clientCert` / `clientKey` называют несуществующий файл |

**Не хватайтесь за `verifyPeer: false`.** Сообщение исчезнет, а вы будете отправлять свой clID, свой
пароль и все коды авторизации трансфера тому, кто ответит по этому адресу, и никак этого не
заметите. Если рукопожатие не проходит проверку, значит связка не та — запросите у реестра
актуальную. `verifyPeerName: false` — послабление поуже (сертификат тот, имя хоста не то), и при
разработке оно иногда оправданно; `verifyPeer: false` не оправдан нигде.

Вход, отклонённый кодом 2200 или 2501, тоже может быть проблемой рядом с TLS, а не неверным паролем:
реестр сверяет IP-адрес отправления со списком разрешённых, а если для вашей учётной записи включена
привязка сертификата, предъявленный клиентский сертификат должен совпадать.

## Открытие и закрытие сессии

```js
await client.connect();     // TLS + чтение <greeting>
await client.login();       // <login>
// … команды …
await client.logout();      // <logout>, ответ 1500; затем сервер закрывает соединение
client.disconnect();        // закрыть сокет локально
```

### `connect()`

```js
const greeting = await client.connect();
```

Открывает TLS-сокет и читает `<greeting>`, которое сервер присылает без запроса, разрешаясь им как
[`Response`](responses.md). Вызывайте его один раз за сессию: он читает ровно один кадр, поэтому
повторный вызов на открытом соединении поглотил бы ответ на что-то другое.

Именно по приветствию клиент и входит. Оно хранится в клиенте и доступно для чтения потом:

```js
client.greeting.value('svID');        // имя сервера
client.greeting.value('svDate');      // его часы, собственной строкой
client.greeting.serviceObjUris();     // ['urn:ietf:params:xml:ns:contact-1.0', …]
client.greeting.serviceExtUris();     // ['urn:ietf:params:xml:ns:secDNS-1.1', …]
client.greeting.isGreeting();         // true
```

До первого `connect()` или `hello()` `client.greeting` равен `null`.

### `hello()`

```js
const greeting = await client.hello();
```

Отправляет `<hello/>` и читает свежее `<greeting>`, которым отвечает сервер, заменяя сохранённое.
Применений два: перечитать меню сервисов без переподключения и не дать простаивающей сессии
закрыться по бездействию. Идентификатора транзакции он не несёт, потому что `<hello>` — не команда.

### `login(newPassword = null)`

```js
const response = await client.login();
```

Отправляет `<login>` с вашими clID и паролем, версией протокола `1.0`, вашим `lang` и сервисами из
приветствия. На 1000 промис разрешается ответом, на всём остальном — отклоняется:

| Код | Поднимается как | Значение |
|---|---|---|
| 2200 | `AuthError` | неверный clID или пароль, IP не из вашего списка разрешённых либо закрытый договор |
| 2002 | `CommandError` | на этом соединении уже выполнен вход |
| 2100 | `CommandError` | версия протокола отклонена |
| 2102 | `CommandError` | запрошенный `lang` не поддерживается |
| 2307 | `CommandError` | объявленный вами сервис не предлагается |
| 2501 | `SessionError` | слишком много неудачных входов — сервер закрывает соединение |
| 2502 | `SessionError` | слишком много одновременных сессий — сервер закрывает соединение |

У каждого из них своё лекарство — потому они и не названы все ошибкой аутентификации: указание
сменить пароль, который был ни при чём, стоит половины рабочего дня. Обратите внимание: на
результате, отличном от 1000, `login()` отклоняет промис **независимо от**
[`throwOnFailure`](commands.md#throwonfailure) — сессию, которая не открылась, разглядывать
бессмысленно.

Для этих двух шагов есть сокращение:

```js
const client = await Client.connectAndLogin(config);   // статический
```

Он создаёт клиента, подключается и входит, разрешаясь готовым клиентом.

### `logout()` и `disconnect()`

```js
await client.logout();     // разрешается кодом ответа 1500
client.disconnect();
```

`logout()` завершает сессию корректно: сервер отвечает 1500 и затем закрывает соединение.
`disconnect()` закрывает сокет с вашей стороны и помечает сессию как завершённую. Он синхронный, не
принимает аргументов и безопасен в любой момент, в том числе когда ничего и не подключалось, —
потому ему и место в блоке `finally`. После `disconnect()` тот же `Client` может снова вызвать
`connect()`: транспорт открывается заново без остатков.

### Где вы находитесь

```js
client.isConnected();   // открыт ли сокет и жив ли он
client.isLoggedIn();    // удался ли login() и не выполнялись ли с тех пор logout()/disconnect()
```

И то и другое — локальное состояние, а не обращение к серверу. `isConnected()` становится ложным в
тот момент, когда транспорт получает необратимую ошибку — тайм-аут чтения, закрытый сокет, — так что
это честная проверка перед повторным использованием долгоживущего клиента. Сессию, которую сервер
разорвал между командами, вы обнаружите на следующей команде как `ConnectionError`.

## Смена пароля

```js
await client.login('new-secret-value');
```

Новый пароль едет в `<newPW>` рядом со старым. **Смена вступает в силу, только если вход удался**, и
со следующей сессии нужно использовать новое значение — поэтому запишите его туда, где ваша
установка хранит секреты, *прежде* чем считать смену завершённой. Длина и старого, и нового значения
проверяется до того, как что-либо будет отправлено.

Два последствия, которые стоит предусмотреть:

- Если новый пароль длиннее 16 символов, нести его может только блок RFC 8807, и тогда учётная
  запись сможет аутентифицироваться лишь там, где это расширение доступно. Если другое ваше ПО
  входит под той же учётной записью туда, где расширения нет, оно начнёт получать отказы. Реестр
  присылает предупреждающее событие на том же входе, который такой пароль задаёт, — прочитайте
  `securityEvents()` у ответа.
- Смена через границу в 16 символов обрабатывается поэлементно: в блок расширения переносится только
  то значение, которому это действительно нужно, поэтому при смене короткого пароля на длинный
  старый уходит в `<pw>`, а новый — в `<loginSec:newPW>`.

## Безопасность входа (RFC 8807)

Там, где сервер предлагает расширение Login Security, вход несёт небольшой блок, опознающий этого
клиента, а сервер отвечает всем, что в этой сессии считает нужным исправить.

```js
for (const event of (await client.login()).securityEvents()) {
  console.warn(`[${event.level}] ${event.type}: ${event.text}`, event.exDate || '');
}
```

Каждое событие — обычный объект с `text` и теми из перечисленных атрибутов, которые оно несло:

| Поле | Значения |
|---|---|
| `type` | `password`, `certificate`, `cipher`, `tlsProtocol`, `newPW`, `stat`, `custom` |
| `level` | `warning` или `error` |
| `name` | какой набор шифров, какая версия TLS или имя события `custom` |
| `exDate` | для `certificate` — точный момент истечения |
| `value`, `duration`, `lang` | в том виде, в каком их несёт событие |

На здоровой сессии список пуст, поэтому любую запись считайте поводом что-то сделать. Чаще всего это
клиентский сертификат на исходе срока: альтернатива — узнать об этом утром того дня, когда он
перестанет работать.

Сервер возвращает их **только клиенту, который отправил блок расширения**, потому что объявление URI
не является свидетельством умения это расширение читать: многие клиенты формируют свой
`<svcExtension>`, просто возвращая содержимое приветствия. Поэтому блок уходит даже тогда, когда в
нём нечего везти. Он опознаёт клиента, и больше из него ничего не берётся:

```xml
<loginSec:userAgent>
  <loginSec:app>EppTools Node SDK 1.0.0</loginSec:app>
  <loginSec:tech>Node v20.11.0</loginSec:tech>
  <loginSec:os>linux</loginSec:os>
</loginSec:userAgent>
```

Чтобы не участвовать, задайте в конфигурации `loginSecurity: false`. Тогда расширение используется
только там, где иного пути нет: паролю длиннее 16 символов, которые вмещает базовый элемент `<pw>`,
ехать больше негде. Отключение означает, что события безопасности вы получать перестанете.

## Журналирование с маскированием секретов

```js
client.setLogger(console);            // или любой объект с debug / info / warn
```

`setLogger()` возвращает клиента, поэтому вызовы связываются в цепочку. Что попадает в журнал:

| Уровень | Что |
|---|---|
| `debug` | каждый кадр в обе стороны: `EPP >> request …`, `EPP << response …`, `EPP << greeting …` |
| `info` | по одной строке на каждую удавшуюся команду: `EPP result 1000 (svTRID=… clTRID=…)` |
| `warn` | та же строка для команды, которую реестр отклонил |

Если у логгера нет `info` или `warn`, библиотека откатывается к `log`. Если нет `debug`, кадры не
журналируются вовсе — и для боевой среды это правильное поведение по умолчанию: там нужны строки с
результатом, а не полезная нагрузка.

**Кадры маскируются до того, как попадут в логгер.** Содержимое любого элемента `<pw>` или `<newPW>`
с любым префиксом пространства имён заменяется на `***`. Это покрывает пароль входа, `<newPW>` при
смене пароля, `<loginSec:pw>` из RFC 8807 и `<pw>` внутри каждого блока `<authInfo>` — то есть код
авторизации трансфера, учётные данные, по которым любой регистратор может увести у вас домен.

Маскирование — это поведение библиотеки на её собственном пути журналирования. Если вы сами
сериализуете `Frame` через `toXml()` и запишете строку в журнал, её никто не замаскировал:
вычеркните секреты сами, прежде чем строка попадёт на диск или в обращение в поддержку.

## Транспорт, если он вам нужен

`Client` принимает необязательные соединение и логгер — так в тестах подменяют транспорт:

```js
const { Client, Connection } = require('@epptools/sdk');

const client = new Client(config, new Connection(config), console);
```

`Connection` — это слой кадрирования по RFC 5734 и ничего больше: семантики EPP он не знает:

| Метод | Что делает |
|---|---|
| `open()` | открывает TLS-сокет; разрешается по завершении рукопожатия |
| `isOpen()` | жив ли сокет и не зафиксирована ли необратимая ошибка |
| `writeFrame(xml)` | пишет один кадр с 4-байтовым префиксом длины в порядке big-endian |
| `readFrame()` | разрешается телом следующего целого кадра в виде строки |
| `close()` | уничтожает сокет |

Кадрирование считает **байты**, а не символы, поэтому кириллица и IDN кадрируются правильно. Процесс
защищают три предела: кадр, объявляющий больше 1 МиБ, отклоняется; непрочитанные данные сверх 4 МиБ
закрывают соединение; и у каждого `readFrame()` свой срок `readTimeout`.

Последний срок намеренно отсчитывается на каждое чтение, а не таймером бездействия сокета:
простаивающей сессии EPP, в которой нет команды в полёте, нечего получать, и таймер бездействия убил
бы совершенно здоровую. **Тайм-аут чтения необратим.** Ответ, пришедший после срока,
рассинхронизировал бы поток — следующее чтение вернуло бы ответ на предыдущую команду, — поэтому
вместо этого закрывается соединение. Что это значит для create или renew, написано в
[Ошибках](errors.md#когда-невозможно-понять-произошло-ли-это).
