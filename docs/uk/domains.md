# Домени

Об'єкти доменів відповідають **RFC 5731**. До них застосовуються чотири розширення: **RFC 5910**
(DNSSEC), **RFC 3915** (відновлення RGP), **RFC 8748** (комісії) та власне розширення реєстру, якщо
воно в нього є.

`client.domain` містить по одному методу на кожну команду EPP. Кожен повертає `Promise<Response>`.

| Метод | Що йде в канал передачі |
|---|---|
| `check(names, fee = null, currency = null)` | `<check><domain:check>` (+ `<fee:check>`) |
| `info(name, authInfo = null, hosts = 'all')` | `<info><domain:info>` |
| `create(name, opts = {})` | `<create><domain:create>` |
| `createBuilder(name)` | той самий `<create>`, зібраний крок за кроком |
| `update(name, opts = {})` | `<update><domain:update>` |
| `updateBuilder(name)` | той самий `<update>`, зібраний крок за кроком |
| `delete(name)` | `<delete><domain:delete>` |
| `renew(name, curExpDate, years = 1, fee = null)` | `<renew><domain:renew>` |
| `transfer(op, name, authInfo = null, years = null, fee = null)` | `<transfer op="…"><domain:transfer>` |
| `restore(name, fee = null)` | `<update>`, що несе `<rgp:restore op="request"/>` |

Кожен приклад нижче припускає підключений `client`, який уже виконав вхід, — див.
[Швидкий старт](quickstart.md). Код відповіді 2000 або вищий за замовчуванням відхиляє проміс
типізованою помилкою, тож приклади читають успішний шлях; таксономію див. у
[Помилках](errors.md), а кожен використаний тут метод доступу — у [Відповідях](responses.md).

## check

```js
check(names, fee = null, currency = null)   // => Promise<Response>
```

Надсилає по одному `<domain:name>` на кожен запис усередині `<domain:check>`. `fee` і `currency`
додають у той самий кадр запит ціни за RFC 8748; ця половина описана в
[Балансі і цінах](balance.md#як-запитати-ціну).

Ім'я, яке неможливо зареєструвати, — це **не** помилка. Воно повертається з `avail="0"` і
причиною всередині відповіді `1000`, тож читайте відповідь, а не покладайтеся на відсутність
винятку.

```js
const r = await client.domain.check(['example.com.ua', 'taken.com.ua']);

r.availability();
// { 'example.com.ua': true, 'taken.com.ua': false }

r.isAvailable('example.com.ua');        // true
r.unavailableReason('taken.com.ua');    // 'in use'

// null означає, що про це ім'я у відповіді не сказано нічого: помилка в аргументі або ім'я,
// про яке реєстр не звітував. Це НЕ те саме, що «зайняте», і трактування його як false
// пропускає реєстрацію, яку ви збиралися зробити.
r.isAvailable('never-asked.com.ua');    // null
```

`isAvailable()` та `unavailableReason()` зіставляють ім'я без урахування регістру, тож ім'я, яке
ви дорогою перевели у верхній регістр, усе одно знайде свою відповідь.

**Коди відповіді:** `1000`. Некоректне ім'я дає `2005`, а зона, яку реєстр не обслуговує, —
`2307`. Запит цін із понад 20 записами відхиляється з `2306` — бібліотека зупиняє його раніше,
кидаючи `ValidationError`, див. [обмеження на кадр](balance.md#обмеження-у-20-записів).

## info

```js
info(name, authInfo = null, hosts = 'all')   // => Promise<Response>
```

Надсилає `<domain:info>` з `<domain:name hosts="…">`. Як реєстратор-власник ви отримуєте повний
запис; для домену, яким ви не володієте, передайте `authInfo` домену другим аргументом, щоб
побачити повний запис замість публічної підмножини.

`hosts` обирає, які хости перелічує відповідь:

| Значення | Що перелічує відповідь |
|---|---|
| `'all'` (типово) | делеговані сервери імен і підпорядковані хости |
| `'del'` | лише делеговані сервери імен |
| `'sub'` | лише підпорядковані хости |
| `'none'` | нічого з цього |

```js
const d = await client.domain.info('example.com.ua');

d.objectName();        // 'example.com.ua'
d.roid();              // 'D1-EXAMPLE'
d.sponsor();           // 'EXAMPLE' — обліковий запис, якому він належить зараз
d.registrarOfRecord(); // ідентифікатор, який публікують WHOIS/RDAP реєстру, або null
d.createdBy();         // crID          d.createdDate();   // crDate
d.updatedBy();         // upID, null, якщо ніколи не змінювався
d.expiryDate();        // '2027-08-16T09:15:00Z' — власний рядок сервера
d.transferDate();      // коли він востаннє змінив власника, або null

d.statuses();          // ['ok'] або ['clientHold', 'clientTransferProhibited', ...]
d.registrant();        // 'C1'
d.contacts();          // { admin: ['C1'], tech: ['EXAMPLE-C2', 'EXAMPLE-C3'] }
d.techContacts();      // ['EXAMPLE-C2', 'EXAMPLE-C3']
d.contactsFor('billing');   // [], коли роль ніхто не обіймає — це законна відповідь
d.allContacts();       // кожен ідентифікатор, включно з реєстрантом, без дублікатів

d.nameservers();            // ['ns1.example.com.ua', 'ns2.example.com.ua']
d.nameserverAddresses();    // вбудовані glue-адреси за іменем; {} у реєстрі з об'єктами хостів
d.subordinateHosts();       // хости, що живуть ПІД цим доменом

d.isSigned();          // true, коли повернулися будь-які дані DNSSEC
d.dsRecords();         // [{ keyTag, alg, digestType, digest }, ...]
d.keyRecords();        // [{ flags, protocol, alg, pubKey }, ...]
d.license();           // номер торгової марки або ліцензії, або null
d.authInfo();          // код трансферу — ніколи не пишіть його в лог
```

Три речі в цій відповіді варто врахувати свідомо.

**Домен у стані викупу все одно повідомляє `ok`.** Стани викупу не є значеннями
`<domain:status>`; вони надходять у `<extension>` і повертаються через `rgpStatus()`. Клієнт,
який читає лише `statuses()`, бачить звичайний `ok` на домені за кілька днів до вилучення.

```js
if (d.rgpStatus().includes('redemptionPeriod')) {
  // Видалений, але ще відновлюваний — див. restore() нижче.
}
```

**`inactive` — це не помилка.** Реєстр обчислює його для домену, у якого замало серверів імен
для делегування, тож ім'я, щойно створене без `nameservers`, повідомляє саме його.

**Дати повертаються власним рядком реєстру**, ніколи як `Date`. Саме реєстр вирішує, на який
календарний день припадає продовження; переформатування через локальну часову зону — це те, як
клієнт починає показувати попередній день і продовжувати відносно нього.

Для домену, яким ви володієте, відповідь може також нести ваші фактичні ціни продовження та
відновлення; читайте їх через `prices()` і `priceChannel()`, описані в
[Балансі і цінах](balance.md#підказки-про-ціну-в-domaininfo).

**Коди відповіді:** `1000`; `2202` (неправильний `authInfo` як у не-власника), `2303` (такого
домену немає).

## create

```js
create(name, opts = {})   // => Promise<Response>
```

Будує `<domain:create>`. Нижче перелічено кожен ключ опцій; **ключ, якого ця бібліотека не знає,
відхиляється ще до побудови кадру**, і в помилці названо найближчий відомий ключ. Цей компроміс
навмисний: помилку в написанні, яку просто відкинули б, супроводжувала б відповідь `1000` — без
тієї частини, яку ви просили, і без жодного слова про це у відповіді; `secdns` замість `secDNS`
реєструє домен непідписаним, і ви дізнаєтеся про це вже в зоні.

| Ключ | Тип | У каналі передачі |
|---|---|---|
| `years` | число | `<domain:period unit="y">`; пропустіть його — і реєстр застосує власне значення за замовчуванням |
| `registrant` | рядок | `<domain:registrant>` |
| `contacts` | `{ role: handle }` або `{ role: [handles] }` | по одному `<domain:contact type="role">` на кожен ідентифікатор |
| `nameservers` | `string[]` або `{ name, addresses }[]` | `<domain:ns>` — див. дві моделі нижче |
| `nameServers` | те саме | прийнятне написання `nameservers` |
| `authInfo` | рядок | `<domain:authInfo><domain:pw>` |
| `license` | рядок | `<registry:create><registry:license>` — якщо ваш реєстр його вимагає |
| `secDNS` | `{ dsData, keyData, maxSigLife }` | `<secDNS:create>` (RFC 5910) |
| `fee` | `'100.00'` або `{ amount, currency }` | `<fee:create>` — обмеження, див. [Баланс і ціни](balance.md#обмеження-суми-яку-ви-погоджуєтеся-сплатити) |

### Контакти: один ідентифікатор на роль або кілька

`contacts` приймає будь-яку з форм, окремо для кожної ролі. RFC 5731 дозволяє повторюваний
`<domain:contact type="…">`, тож кожен ідентифікатор отримує власний елемент:

```js
contacts: { admin: 'C1', tech: ['EXAMPLE-C2', 'EXAMPLE-C3'] }
```

Ідентифікатори обрізаються від пробілів, а порожній відкидається, а не надсилається порожнім
елементом.

### Сервери імен: дві моделі, які ніколи не змішуються

Сервер імен — це або **ім'я**, тобто посилання на [об'єкт хоста](hosts.md), який уже існує в
реєстрі, або ім'я **з вбудованими glue-адресами**. Запитайте свій реєстр, яку модель він приймає.

```js
// Об'єкти хостів, створені заздалегідь через client.host.create():
nameservers: ['ns1.example.com.ua', 'ns2.example.com.ua']

// Або glue-адреси, вбудовані разом з іменем:
nameservers: [
  { name: 'ns1.example.com.ua', addresses: ['203.0.113.1', '2001:db8::1'] },
  { name: 'ns2.example.com.ua', addresses: ['203.0.113.2'] },
]
```

IPv4 та IPv6 розрізняються автоматично, тож вам ніколи не доводиться писати атрибут `ip`
самостійно.

RFC 5731 робить `<domain:ns>` вибором між двома формами, тож одна команда використовує одну
модель. Змішаний список тут дає `ValidationError`, а не голий `2001` від реєстру, який не називає
жодного поля.

### authInfo

`<domain:authInfo>` обов'язковий під час create, тому бібліотека завжди його виводить. Задайте
власний код трансферу — або пропустіть ключ, і тоді піде порожній `<domain:pw/>`, що просить
реєстр застосувати власну політику зони й згенерувати код. Будь-хто, хто має це значення, може
перевести домен до іншого реєстратора: ставтеся до нього як до облікових даних, тримайте його
поза логами й зверненнями та змінюйте після того, як передали клієнту.

### Повний create із прочитаною відповіддю

```js
const created = await client.domain.create('example.com.ua', {
  years: 1,
  registrant: 'C1',
  contacts: { admin: 'C1', tech: ['EXAMPLE-C2', 'EXAMPLE-C3'] },
  nameservers: ['ns1.example.com.ua', 'ns2.example.com.ua'],
  authInfo: 'D0main-Pw',
});

created.code();          // 1000 або 1001, коли реєстр виконує команду асинхронно
created.objectName();    // 'example.com.ua'
created.createdDate();   // '2026-08-16T09:15:00Z'
created.expiryDate();    // '2027-08-16T09:15:00Z' — власний рядок реєстру
created.feeAmount();     // '100.00', коли реєстр повернув комісію, інакше null
created.feeCurrency();   // 'UAH'
created.svTRID();        // збережіть це: саме за ним підтримка знаходить транзакцію

if (created.isPending()) {
  // 1001 означає «прийнято», а не «завершено». Результат надійде пізніше як poll-сповіщення,
  // paTRID якого несе ЦЕЙ svTRID — збережіть його, інакше ви не зрозумієте, якої саме операції
  // в очікуванні стосується сповіщення. Див. Poll.
  await recordPending(created.svTRID(), 'example.com.ua');
}
```

### DNSSEC під час create

```js
await client.domain.create('example.com.ua', {
  years: 1,
  registrant: 'C1',
  secDNS: {
    maxSigLife: 1209600,
    dsData: [{ keyTag: 12345, alg: 13, digestType: 2, digest: '49FD46E6C4B45C55D4AC' }],
  },
});
```

`secDNS` приймає `dsData`, `keyData` та `maxSigLife`. DS-запис може нести DNSKEY, з якого його
обчислено, як `keyData` всередині запису: реєстр, який це приймає, перевіряє дайджест за ключем
замість вас, а той, який не приймає, відповідає `2306`, а не ігнорує зайвий елемент:

```js
secDNS: {
  dsData: [{
    keyTag: 12345, alg: 13, digestType: 2, digest: '49FD46E6C4B45C55D4AC',
    keyData: { flags: 257, protocol: 3, alg: 13, pubKey: 'AwEAAb...' },
  }],
}
```

RFC 5910 вимагає щонайменше одного запису в `<secDNS:create>`, тож об'єкт `secDNS`, у якому немає
ні `dsData`, ні `keyData`, взагалі не виводить блоку розширення — замість того, щоб вивести
недійсний порожній.

### Ліцензія під час create

Деякі реєстри не реєструють окремі імена без номера торговельної марки або ліцензії — найчастіше це
короткі й дорогі імена безпосередньо під доменом верхнього рівня:

```js
await client.domain.create('example.com.ua', {
  years: 1, registrant: 'C1', license: 'TM-2026-000123',
});
```

Він їде у **власному** розширенні реєстру, і його простір імен клієнт читає з `<greeting>` — див.
[Команди](commands.md#власні-розширення-вашого-реєстру). Реєстру, який такого розширення не оголошує,
замість кадру, який той би проігнорував, буде кинуто `ConfigError`.

Яким саме іменам вона потрібна — це політика реєстру, а не протоколу, тож питайте у свого. Про те,
що ви не вгадали, скажуть дві відмови: ім'я, якому ліцензія потрібна, але її не передали, зазвичай
отримує `2003` (бракує обов'язкового параметра), а ліцензія, надіслана туди, де на неї не чекають, —
`2306` (неприпустиме за політикою значення параметра).

**Коди відповіді:** `1000`; `1001`, коли команду поставлено в чергу; `2003` / `2004` / `2005` /
`2306` (валідація та політика), `2104` (недостатній баланс — див. [Баланс](balance.md)), `2302`
(вже зареєстровано), `2103` (DNSSEC у цій зоні не пропонується), `2307` (зона не обслуговується),
`2004`, коли обмеження ціни нижче за реальну ціну.

## createBuilder

```js
createBuilder(name)   // => DomainCreateBuilder
```

Та сама команда, зібрана по одному названому кроку за раз. Власного XML він не будує: `send()`
передає опції прямо в `create()`, тож кадр ідентичний, і кожна перевірка, що діє для одного, діє
й для іншого. Змінюється те, що помилка в написанні стає неіснуючим методом, про який вам скаже
редактор.

```js
const response = await client.domain.createBuilder('example.com.ua')
  .years(1)
  .registrant('C1')
  .adminContact('C1')
  .techContact('EXAMPLE-C2').techContact('EXAMPLE-C3')   // накопичується
  .nameserver('ns1.example.com.ua').nameserver('ns2.example.com.ua')
  .authInfo('D0main-Pw')
  .maxFee('180.00', 'UAH')
  .send();
```

Кожен крок описано в [Білдерах](builders.md).

## update

```js
update(name, opts = {})   // => Promise<Response>
```

Оновлення в EPP — це **дельта**, а не заміна. Те, до якого блоку належить зміна, і є всією
семантикою команди:

| Блок | Ключі | Значення |
|---|---|---|
| `add` | `ns`, `contacts`, `statuses` | приєднати ці, зберігши те, що вже є |
| `rem` | `ns`, `contacts`, `statuses` | від'єднати рівно ці |
| `chg` | `registrant`, `authInfo`, `clearAuthInfo` | замінити значення |

Поряд із ними — чотири ключі, що їдуть у `<extension>`:

| Ключ | Тип | У каналі передачі |
|---|---|---|
| `secDNS` | `{ add, rem, remAll, maxSigLife }` | `<secDNS:update>` (RFC 5910) |
| `restore` | `true` | `<rgp:update><rgp:restore op="request"/>` (RFC 3915) |
| `license` | рядок | `<registry:update><registry:license>` |
| `fee` | `'100.00'` або `{ amount, currency }` | `<fee:update>` — обмеження |

`add.ns` і `rem.ns` приймають ті самі дві моделі серверів імен, що й `create`, з тим самим
правилом проти змішування їх в одній команді.

```js
const r = await client.domain.update('example.com.ua', {
  add: { ns: ['ns3.example.com.ua'], statuses: ['clientTransferProhibited'] },
  rem: { ns: ['ns2.example.com.ua'] },
  chg: { registrant: 'EXAMPLE-C9', authInfo: 'N3w-D0main-Pw' },
});

r.code();        // 1000 або 1001, коли реєстр виконує команду асинхронно
r.isPending();
```

Встановлювати й знімати ви можете лише **клієнтські** статуси: `clientHold`,
`clientDeleteProhibited`, `clientUpdateProhibited`, `clientTransferProhibited`,
`clientRenewProhibited`. Статуси `server*` належать реєстру, а `ok` та `inactive` обчислюються —
їх не встановлює ніхто.

Оновлення не повертає нічого про об'єкт, тож перечитайте його через `info()`, коли вам потрібно
підтвердити результат, а не просто прийняття команди.

### Відкликання розголошеного коду трансферу

`chg.clearAuthInfo: true` виводить `<domain:authInfo><domain:null/></domain:authInfo>`, що
**видаляє** код трансферу.

```js
await client.domain.update('example.com.ua', { chg: { clearAuthInfo: true } });
```

Це не те саме, що встановити порожній код. Порожній `<domain:pw/>` зберігає порожній рядок —
значення, яке його власник усе ще може пред'явити, тож домен лишається рівно таким самим рухомим,
яким був: витік не закрито. Очищає код лише null-форма. Коли клієнту знову знадобиться код,
задайте новий через `chg.authInfo`.

Ці два варіанти взаємовиключні: схема не може виразити обидва, а передача їх разом дає
`ValidationError` ще до того, як щось надіслано.

### DNSSEC під час update

Тут оновлення теж є дельтою і не використовує повторно форму create:

| Ключ | Дія |
|---|---|
| `add` | `{ dsData: [...], keyData: [...] }` — додати ці ключі |
| `rem` | `{ dsData: [...], keyData: [...] }` — видалити рівно ці; кожне поле має збігатися з тим, що зберігає реєстр |
| `remAll: true` | видалити всі ключі |
| `maxSigLife` | змінити час життя підпису в секундах; може їхати окремо |

```js
// Замінити весь набір ключів однією командою, без проміжку, коли домен лишається непідписаним.
await client.domain.update('example.com.ua', {
  secDNS: {
    remAll: true,
    add: { dsData: [{ keyTag: 54321, alg: 13, digestType: 2, digest: 'A1B2C3D4E5F60718293A' }] },
  },
});
```

`remAll` і поіменний `rem` взаємовиключні. Об'єкт `secDNS`, який не виражає жодної зміни, не
виводить блоку `<secDNS:update>`, бо порожній блок для реєстру — синтаксична помилка (`2003`), а
не «нічого не робити»: клієнт, який будує блок беззастережно й заповнює його лише інколи, зазнає
невдачі саме в тих випадках, коли блок порожній.

**Коди відповіді:** `1000`; `1001`, коли команду поставлено в чергу; `2003` / `2004` / `2005` /
`2306`, `2303`, `2304` (статус забороняє), `2305`.

## updateBuilder

```js
updateBuilder(name)   // => DomainUpdateBuilder
```

Білдер оновлення називає блок, у який потрапляє кожна зміна, тож дельта видна прямо у виклику:

```js
await client.domain.updateBuilder('example.com.ua')
  .addNameserver('ns3.example.com.ua')
  .remNameserver('ns2.example.com.ua')
  .addStatus('clientTransferProhibited')
  .changeRegistrant('EXAMPLE-C9')
  .clearAuthInfo()
  .send();
```

Нічого не надсилається до `send()`, і білдер надсилає один раз — другий `send()` відхиляється,
бо надіслати двічі означало б дві команди, а для платної — і два списання. Див.
[Білдери](builders.md).

## delete

```js
delete(name)   // => Promise<Response>
```

```js
const r = await client.domain.delete('example.com.ua');
r.code();   // 1000 або 1001, коли поставлено в чергу
```

Домен, видалений у межах свого вікна add-grace, зникає негайно. Інакше він переходить у
`redemptionPeriod` і його можна повернути через [`restore()`](#restore) протягом вікна
відновлення; після цього він переходить у `pendingDelete` і вилучається.

Підпорядковані хости блокують видалення. Перевірте їх спершу — відповідь уже є в прочитаному вами
`info()`:

```js
const d = await client.domain.info('example.com.ua');
if (d.subordinateHosts().length) {
  // Інакше 2305: вони живуть під доменом і мають зникнути першими.
}
```

**Коди відповіді:** `1000`; `1001`, коли поставлено в чергу; `2303`, `2304` (наприклад, статус
`clientDeleteProhibited`), `2305` (щось усе ще прикріплено).

## renew

```js
renew(name, curExpDate, years = 1, fee = null)   // => Promise<Response>
```

`curExpDate` має дорівнювати **поточній даті завершення терміну реєстрації** домену, і цей
елемент — дата, а не позначка часу, а `info()` віддає завершення повною позначкою часу.
**Передавайте її як є:** денну частину бібліотека візьме сама.

Береться вона такою, якою її написав сервер, без розбору і без переведення часових поясів. Це
зроблено навмисно: позначки часу в EPP — в UTC, і дата завершення в реєстру теж у UTC, тож клієнт,
який переформатовує її через локальну зону — а `new Date(...)` до цього й підштовхує, — для кожного
домену, що завершується близько опівночі, влучає на добу в той чи інший бік і далі продовжує за
датою, якої в реєстру немає. Переводьте в місцевий час там, де показуєте, а не перед надсиланням
назад.

```js
const d = await client.domain.info('example.com.ua');
const currentExpiry = d.expiryDate();            // '2027-08-16T09:15:00Z'

const r = await client.domain.renew('example.com.ua', currentExpiry, 1);   // піде '2027-08-16'

r.objectName();    // 'example.com.ua'
r.expiryDate();    // НОВА дата завершення, як її записав реєстр
r.feeAmount();     // скільки це коштувало, коли реєстр повернув комісію
```

Невідповідний `curExpDate` дає `2105`, і це запобіжник, а не незручність: він не дає застарілому
запису у вашій системі продовжити домен, який уже продовжено. Читайте поточну дату завершення
безпосередньо перед продовженням, а не з кешу.

Передайте `fee`, щоб обмежити суму, яку ви погоджуєтеся сплатити, — див.
[Баланс і ціни](balance.md#обмеження-суми-яку-ви-погоджуєтеся-сплатити).

**Коди відповіді:** `1000`; `2004` (період поза діапазоном), `2105` (невідповідність
`curExpDate`, або домен неможливо продовжити), `2104` (недостатній баланс), `2303`, `2304`,
`2306`.

## transfer

```js
transfer(op, name, authInfo = null, years = null, fee = null)   // => Promise<Response>
```

`op` — це одне з `'request'`, `'approve'`, `'reject'`, `'cancel'`, `'query'`, і воно стає
атрибутом `op` елемента `<transfer>`.

| `op` | Хто надсилає | Дія |
|---|---|---|
| `request` | реєстратор, що приймає | запитує домен, надаючи його `authInfo` |
| `query` | будь-яка зі сторін | повідомляє, на якій стадії запит, нічого не змінюючи |
| `approve` | поточний власник | приймає запит, що очікує |
| `reject` | поточний власник | відмовляє в запиті, що очікує |
| `cancel` | реєстратор, що запитує | відкликає власний запит |

```js
const r = await client.domain.transfer('request', 'example.com.ua', 'the-code');

r.code();              // 1001 — прийнято, не завершено
r.transferStatus();    // 'pending'
r.transfer();
// { status: 'pending',
//   requestedBy: 'EXAMPLE',    requestedAt: '2026-08-16T09:15:00Z',
//   actingClient: 'DELTA',   actBy:       '2026-08-21T09:15:00Z',
//   expiryDate: '2028-08-16T09:15:00Z' }
```

`actBy` — це строк, і він важливий для обох сторін: **мовчання завершує трансфер.** Після цього
моменту реєстр підтверджує трансфер, а не скасовує його, тож реєстратор, що втрачає домен і
підшиває сповіщення замість того, щоб відповісти на нього, втратить домен. Обидві сторони
дізнаються про кожен крок через [poll](poll.md), а поки встановлено `pendingTransfer`, жодна інша
операція з доменом не приймається.

`years` відображається в `<domain:period>`, а те, чи взагалі трансфер його приймає, — це політика
реєстру, а не протоколу. Спитайте у свого, як влаштовано в нього:

- **Трансфер продовжує домен.** Він включає обов'язкове продовження, тарифікується і збільшує
  термін реєстрації. Передайте кількість років — зазвичай `1` — або лишіть `years` як `null`, щоб
  пропустити елемент і взяти значення реєстру за замовчуванням. Значення, якого реєстр не
  припускає, відхиляється з `2004`.
- **Трансфер лише переносить домен.** Він безплатний, і термін реєстрації не змінюється. Лишіть
  `years` як `null`, щоб `<domain:period>` не надсилався.

Літеральний `0` — це не спосіб сказати «жодного»: схемний тип елемента починається з 1, тож кадр
буде відхилено як синтаксичну помилку (`2001`) ще до будь-якої перевірки політики. Сказати «жодного»
означає передати `null`.

Там, де зона не використовує кодів авторизації, лишіть `authInfo` як `null` — і `<domain:authInfo>`
не надсилається.

Підтвердження, відмова, скасування та запит стану не потребують ані коду, ані періоду:

```js
await client.domain.transfer('approve', 'example.com.ua');
await client.domain.transfer('reject',  'example.com.ua');
await client.domain.transfer('cancel',  'example.com.ua');

const q = await client.domain.transfer('query', 'example.com.ua');
q.transfer().actBy;    // скільки часу ще лишається у власника
```

**Коди відповіді:** `1000` / `1001`; `2201` (не ваш об'єкт), `2202` (неправильний `authInfo`),
`2300` (вже очікує), `2301` (немає чого підтверджувати), `2304`, `2306`, `2106` (не підлягає
трансферу), `2104` для платного трансферу без коштів.

## restore

```js
restore(name, fee = null)   // => Promise<Response>
```

Відновлення за RFC 3915. Це доменний `<update>`, єдиним вмістом якого є
`<rgp:restore op="request"/>`, і саме це будує метод: він викликає `update()` з `restore: true` і
нічим більше, бо жодні `add`, `rem` чи `chg` не можуть супроводжувати відновлення.

```js
const d = await client.domain.info('example.com.ua');

if (d.rgpStatus().includes('redemptionPeriod')) {
  const r = await client.domain.restore('example.com.ua', '1000.00');
  r.code();        // 1000 або 1001, коли воно завершується асинхронно
  r.feeAmount();   // скільки коштувало відновлення
}
```

Другий аргумент — це максимум, який ви погоджуєтеся сплатити, а не опублікована ціна.
Відновлення — одна з найдорожчих операцій життєвого циклу, і обмеження — це різниця між відмовою,
яку ви можете показати клієнту, і списанням, яке доведеться пояснювати, — див.
[Баланс і ціни](balance.md#обмеження-суми-яку-ви-погоджуєтеся-сплатити).

Відновлення працює лише в межах вікна відновлення. Після нього ім'я вивільняється, і відповіддю
буде те, що домену не існує.

**Коди відповіді:** `1000` або `1001`; `2104`, `2303`, `2304` (домен не у стані викупу), `2306`.

## Коли операція не вдалася, а ви не знаєте, чи вона відбулася

Тайм-аут читання або обірване з'єднання посеред `create`, `renew`, `transfer` чи `restore`
лишають справді невідомий результат: реєстр міг виконати команду і списати з вас кошти ще до
того, як відповідь загубилася.

**Не повторюйте команду просто так.** Сліпий повтор — це те, як домен реєструють і оплачують
двічі. Натомість запитайте в реєстру, як є насправді: `info()` після create, а після renew —
порівняйте `expiryDate()` з тим, чого ви очікували. Повторюйте, лише якщо об'єкт справді
перебуває в тому стані, з якого ви починали. Повне правило — у [Помилках](errors.md).
