# Контакти

Об'єкти контактів відповідають **RFC 5733**. У кожному процесі надання послуг вони йдуть першими:
[домен](domains.md) посилається на свого реєстранта й рольові контакти за ідентифікатором, тож
контакти мають існувати раніше за домен.

`client.contact` містить по одному методу на кожну команду EPP. Кожен повертає `Promise<Response>`.

| Метод | Що йде в канал передачі |
|---|---|
| `check(ids)` | `<check><contact:check>` |
| `info(id, authInfo = null)` | `<info><contact:info>` |
| `create(id, opts = {})` | `<create><contact:create>` |
| `createAuto(opts = {})` | той самий `<create>` під зарезервованим ідентифікатором |
| `createBuilder(id, email)` | той самий `<create>`, зібраний крок за кроком |
| `update(id, opts = {})` | `<update><contact:update>` |
| `updateBuilder(id)` | той самий `<update>`, зібраний крок за кроком |
| `delete(id)` | `<delete><contact:delete>` |
| `transfer(op, id, authInfo = null)` | `<transfer op="…"><contact:transfer>` |

Кожен приклад нижче припускає підключений `client`, який уже виконав вхід, — див.
[Швидкий старт](quickstart.md). Таксономію винятків див. у [Помилках](errors.md), а кожен
використаний тут метод доступу — у [Відповідях](responses.md).

---

## check

```js
check(ids)   // => Promise<Response>
```

Надсилає по одному `<contact:id>` на кожен запис. `avail` тут означає, що **ідентифікатор
вільний**, а не що контакт існує: ви перевіряєте ім'я, яке хочете зайняти.

```js
const r = await client.contact.check(['C1', 'EXAMPLE-C2']);

r.availability();                  // { 'C1': false, 'EXAMPLE-C2': true }
r.isAvailable('EXAMPLE-C2');      // true
r.unavailableReason('C1');// 'in use' або null
```

Якщо у вас немає власної схеми найменування, повністю обійдіть перегони «перевір, потім займи» і
дозвольте реєстру згенерувати ідентифікатор — див. [createAuto](#createauto).

**Коди відповіді:** `1000`.

## info

```js
info(id, authInfo = null)   // => Promise<Response>
```

Як реєстратор-власник ви отримуєте повний запис. Для контакту, яким ви не володієте, передайте
його `authInfo`, щоб побачити повний запис замість публічної підмножини.

```js
const c = await client.contact.info('C1');

c.objectName();     // 'C1' — ІДЕНТИФІКАТОР, а не ім'я людини
c.roid();
c.sponsor();        // clID
c.createdBy();      c.createdDate();
c.updatedBy();      c.updatedDate();
c.statuses();       // ['ok'] або ['linked', 'clientUpdateProhibited', ...]

c.email();          // 'contact@example.com'
c.voice();          // '+380.441234567'
c.fax();            // null, коли контакт його не має
c.authInfo();       // код трансферу — ніколи не пишіть його в лог

c.postalInfo();
// { int: { name: 'Ivan Petrenko', org: 'Pryklad LLC', street: ['vul. Khreshchatyk 1'],
//          city: 'Kyiv', sp: '', pc: '01001', cc: 'UA' },
//   loc: { name: 'Іван Петренко', ... } }

c.disclose();       // { flag: false, elements: ['email', 'voice'] } або null
```

`postalInfo()` повертає лише ті форми, які реєстр справді надіслав, з ключем за формою; контакт
зазвичай несе тільки одну. Відсутні частини повертаються як `''`, а не як відсутні ключі, тож
шаблон може читати `.pc` без перевірок.

Статус `linked` означає, що на контакт посилається принаймні один об'єкт, — саме через це
видалення завершується помилкою `2305`.

**Коди відповіді:** `1000`; `2202` (неправильний `authInfo` як у не-власника), `2303`.

## create

```js
create(id, opts = {})   // => Promise<Response>
```

| Ключ | Тип | У каналі передачі |
|---|---|---|
| `name` | рядок | `<contact:name>` в єдиному поштовому блоці |
| `org` | рядок | `<contact:org>`, надсилається лише непорожнім |
| `street` | `string[]` | по одному `<contact:street>` на рядок, до 3 |
| `city` | рядок | `<contact:city>` |
| `sp` | рядок | `<contact:sp>` (область / регіон), надсилається лише непорожнім |
| `pc` | рядок | `<contact:pc>` (поштовий індекс), надсилається лише непорожнім |
| `cc` | рядок | `<contact:cc>` — дволітерний код країни |
| `type` | `'int'` \| `'loc'` | атрибут `type` цього блоку; типово `'int'` |
| `postalInfos` | `PostalInfo[]` | по одному `<contact:postalInfo>` на запис — використовуйте це для обох форм |
| `voice` | рядок | `<contact:voice>`, надсилається лише непорожнім |
| `fax` | рядок | `<contact:fax>`, надсилається лише непорожнім |
| `email` | рядок | `<contact:email>` — **обов'язковий** |
| `authInfo` | рядок | `<contact:authInfo><contact:pw>` |
| `disclose` | об'єкт | `<contact:disclose>` — див. [Розкриття даних](#розкриття-даних) |

Ключ, якого ця бібліотека не знає, відхиляється ще до побудови кадру, і в помилці названо
найближчий відомий ключ. Ключ із помилкою в написанні, який просто відкинули б, усе одно дав би
`1000` — без поля, яке ви збиралися задати, і без жодного слова про це у відповіді.

RFC 5733 вимагає `email`, тож порожній тут кидає `ValidationError`, а не їде до реєстру, щоб
повернутися звідти як `2003`.

`<contact:authInfo>` виводиться завжди. Пропустіть ключ — і піде порожній `<contact:pw/>`, що
просить реєстр застосувати власну політику.

### Дві поштові форми

Контакт несе один або два блоки `<contact:postalInfo>`, і різниця між ними не косметична:

| Форма | Письмо | Призначення |
|---|---|---|
| `int` | **лише ASCII / латиниця** | форма, яку реєстр може представити будь-якій стороні будь-де |
| `loc` | місцеве письмо, напр. кирилиця | адреса в тому вигляді, як її справді написав реєстрант |

Кирилиця в блоці `int` відхиляється з `2005`. Потрібен принаймні один блок; надсилайте обидва,
коли маєте обидва, — тут нічого не відкидається, і `info` повертає все, що ви надіслали.

Плоскі ключі будують один блок. Для обох форм використовуйте `postalInfos`:

```js
const r = await client.contact.create('C1', {
  postalInfos: [
    { type: 'int',
      name: 'Ivan Petrenko', org: 'Pryklad LLC',
      street: ['vul. Khreshchatyk 1'], city: 'Kyiv', pc: '01001', cc: 'UA' },
    { type: 'loc',
      name: 'Іван Петренко', org: 'ТОВ «Приклад»',
      street: ['вул. Хрещатик 1'], city: 'Київ', pc: '01001', cc: 'UA' },
  ],
  voice: '+380.441234567',
  email: 'contact@example.com',
  authInfo: 'C0ntact-Pw',
});

r.code();          // 1000
r.objectName();    // 'C1'
r.createdDate();   // '2026-08-16T09:15:00Z' — власний рядок реєстру
```

Номери телефону й факсу подаються у формі EPP `+CC.NNNNNNNNN`.

### Розкриття даних

`disclose` — це перемикач приватності з RFC 5733. `flag` визначає напрям, а перелічені елементи —
те, до чого він застосовується; до всього, що **не** перелічено, застосовується протилежне, тож
список без прапорця не означає нічого.

```js
// Публікувати лише адресу e-mail і номер телефону.
disclose: { flag: false, addr: ['int', 'loc'], name: ['int', 'loc'], org: ['int', 'loc'] }

// Або в іншому напрямі: ці елементи можна публікувати.
disclose: { flag: true, voice: true, email: true }
```

| Поле | Значення |
|---|---|
| `flag` | `true` = перелічені елементи можна публікувати; `false` = їх треба приховати |
| `name`, `org`, `addr` | масив форм: `['int']`, `['loc']` або обидві |
| `voice`, `fax`, `email` | `true`, щоб внести елемент до списку |

`name`, `org` та `addr` існують по одному на кожну поштову форму, тож вибір робиться для кожної
форми окремо. Якщо назвати лише `['int']`, форма місцевим письмом лишиться публічною — це
налаштування приватності має вигляд застосованого, але таким не є.

Прапорець читається за тим, що він означає, а не за «істинністю» в JavaScript: `'0'`, `'false'` та
`''` приходять з HTML-форм і навантажень JSON, і всі три в JS є істинними рядками. Тут вони
означають **приховати** — саме так, як написав той, хто викликав.

Прочитати налаштування назад можна через `disclose()`, який повертає `{ flag, elements }` із
суфіксами форм — `['name:int', 'name:loc', 'email']`.

**Коди відповіді:** `1000`; `2003` (немає поштового блоку або немає e-mail), `2005` (поганий
синтаксис — некоректний e-mail або кирилиця в блоці `int`), `2302` (ідентифікатор зайнято),
`2306`.

## createAuto

```js
createAuto(opts = {})   // => Promise<Response>
Contact.AUTO_ID         // 'autonic' — зарезервований ідентифікатор
```

Надсилає той самий create під зарезервованим ідентифікатором контакту, що просить реєстр **обрати
ідентифікатор** замість вас. Згенерований ідентифікатор повертається у відповіді, і ця відповідь —
єдине місце, де він з'являється:

```js
const r = await client.contact.createAuto({
  name: 'Pryklad LLC', city: 'Kyiv', cc: 'UA', email: 'contact@example.com',
});

const handle = r.objectName();   // 'c-9f4b2ad10e' — збережіть його негайно
await saveContactHandle(handle);
```

Користуйтеся ним, коли у вас немає власної схеми найменування і коли інакше довелося б писати цикл
повторів навколо `2302`, бо хтось інший зайняв ідентифікатор між вашими `check` і `create`.
**Кожен виклик генерує новий ідентифікатор**, тож повтор дає другий контакт, а не колізію, — а
отже, сліпий повтор після втраченої відповіді лишає вас із двома контактами, а не з одним.
Звіряйте свої записи, перш ніж повторювати.

Це значення є запитом, а не іменем: воно не зберігається як ідентифікатор, тож лишається придатним
для всіх. Якщо ви волієте передавати його явно — наприклад, через білдер, — воно експортується як
константа:

```js
const { Contact } = require('@epptools/sdk');

await client.contact.createBuilder(Contact.AUTO_ID, 'contact@example.com')
  .internationalAddress({ name: 'Pryklad LLC', city: 'Kyiv', countryCode: 'UA' })
  .send();
```

**Коди відповіді:** ті самі, що й у [create](#create), окрім `2302` — немає ідентифікатора, з яким
можна зіткнутися.

## createBuilder

```js
createBuilder(id, email)   // => ContactCreateBuilder
```

Та сама команда, зібрана по одному названому кроку за раз. Ідентифікатор та e-mail є аргументами,
а не кроками, бо реєстр вимагає обох, а крок — це те, що можна забути. `send()` викликає
`create()`, тож кадр ідентичний.

```js
const r = await client.contact.createBuilder('C1', 'contact@example.com')
  .internationalAddress({
    name: 'Ivan Petrenko', org: 'Pryklad LLC',
    street: ['vul. Khreshchatyk 1'], city: 'Kyiv', postalCode: '01001', countryCode: 'UA',
  })
  .localizedAddress({
    name: 'Іван Петренко', city: 'Київ', countryCode: 'UA',
  })
  .voice('+380.441234567')
  .authInfo('C0ntact-Pw')
  .withhold('addr', 'voice')
  .send();
```

Кожен крок описано в [Білдерах](builders.md).

## update

```js
update(id, opts = {})   // => Promise<Response>
```

| Ключ | Тип | У каналі передачі |
|---|---|---|
| `addStatuses` | `string[]` | один `<contact:add>`, що містить по одному `<contact:status s="…">` на запис |
| `remStatuses` | `string[]` | один `<contact:rem>`, так само |
| `chg` | об'єкт | `<contact:chg>` — поля нижче |

`chg` приймає `postalInfo` (один блок), `postalInfos` (масив блоків), `voice`, `fax`, `email`,
`authInfo` та `disclose` і виводить їх у порядку, зафіксованому RFC 5733.

```js
await client.contact.update('C1', {
  chg: { email: 'new-contact@example.com', voice: '+380.441234599' },
  addStatuses: ['clientUpdateProhibited'],
});
```

Встановлювати й знімати ви можете лише **клієнтські** статуси. `linked` та `ok` обчислює реєстр, а
статуси `server*` належать йому.

### Правило оновлення: поштовий блок ЗАМІЩУЄТЬСЯ, а не зливається

Надішліть поштовий блок у `chg` — і реєстр **замістить** ним той, що тримає. Їх не зливають поле за
полем, тож усе, чого ви не подали, зникає.

RFC 5733 можна прочитати й інакше: у `chgPostalInfoType` кожна зі складових — name, org, addr —
необов'язкова, і це схоже на «не подавайте її, і реєстр збереже те, що має». Це читання небезпечне:
проти реєстру, який заміщає блок, **кожна з цих команд відповідає 1000**:

| Що ніс `chg` | Що лишилося в контакті |
|---|---|
| повний блок із `org: ''` | організацію прибрано, адреса недоторкана |
| повний блок без ключа `org` | організацію **також прибрано** |
| самий лише `{ org: '' }` | **поштового блоку немає взагалі** — ані імені, ані вулиці, міста, індексу чи країни |

Тобто змінити одне поле адреси неможливо, і збій мовчазний: команда успішна, а даних немає. `name`,
`city` і `cc` обов'язкові в кожній поштовій зміні, і цей SDK без них відмовляє, — але ця перевірка
лише тримає кадр валідним і не здатна повернути `org`, `sp` чи `pc`, якого ви не подали.

**Прочитайте блок, застосуйте свою зміну і надішліть його цілим:**

```js
const current = (await client.contact.info('C1')).postalInfo().int;

// Перенести контакт і прибрати організацію, лишивши решту такою, як була.
await client.contact.update('C1', {
  chg: { postalInfo: { ...current, type: 'int', city: 'Lviv', org: '' } },
});
```

Чого заміщення не досягає — то це другої поштової форми: `int` і `loc` адресуються окремо, тож
заміна однієї лишає другу точно такою, як була.

Усередині блоку, який ви надсилаєте, порожній рядок так само очищає необов'язкове поле:

| Що ви пишете | Що відбувається |
|---|---|
| ключ містить значення | поле встановлюється в нього |
| ключ містить `''` | поле надсилається порожнім, що **очищає** його |
| ключа немає | поле не надсилається — і реєстр видаляє те, що тримав |

Зміна однієї форми лишає іншу недоторканою: `{ type: 'loc', … }` ніколи не зачіпає міжнародний
блок.

### Для контакту немає clearAuthInfo

`chg.authInfo` **замінює** код трансферу. RFC 5731 дає домену null-форму для видалення коду; RFC
5733 не визначає для контакту нічого рівнозначного, тож код контакту можна замінити, але не
видалити. Не хапайтеся за порожній пароль як за замінник: порожнє значення — це все одно
значення, яке його власник може пред'явити.

**Коди відповіді:** `1000`; `2303`, `2304`, `2306`.

## updateBuilder

```js
updateBuilder(id)   // => ContactUpdateBuilder
```

```js
await client.contact.updateBuilder('C1')
  .changeEmail('new-contact@example.com')
  .changeInternationalAddress({ city: 'Lviv', countryCode: 'UA', org: '' })
  .addStatus('clientUpdateProhibited')
  .send();
```

Діє те саме правило наявності: поле, якого ви не передали, не надсилається, а `''` очищає. Нічого
не доходить до реєстру до `send()`, і білдер надсилає один раз. Див. [Білдери](builders.md).

## delete

```js
delete(id)   // => Promise<Response>
```

```js
await client.contact.delete('C1');
```

**Контакт, на який усе ще посилається домен, видалити неможливо** — реєстр відповідає `2305`, і це
надходить як `ObjectStatusError`. Спершу відкріпіть його: змініть реєстранта або рольовий контакт
домену через [`domain.update()`](domains.md#update), а потім видаляйте. `allContacts()` у
відповіді domain info скаже, які ідентифікатори домен усе ще тримає.

**Коди відповіді:** `1000`; `2303`, `2305` (усе ще пов'язаний).

## transfer

```js
transfer(op, id, authInfo = null)   // => Promise<Response>
```

`op` — це одне з `'request'`, `'approve'`, `'reject'`, `'cancel'`, `'query'`. Трансфер контакту не
несе ані періоду, ані комісії — лише ідентифікатор і, для запиту, `authInfo` контакту.

| `op` | Хто надсилає | Дія |
|---|---|---|
| `request` | реєстратор, що приймає | запитує контакт, надаючи його `authInfo` |
| `query` | будь-яка зі сторін | повідомляє стан запиту, що очікує |
| `approve` | поточний власник | приймає його |
| `reject` | поточний власник | відмовляє в ньому |
| `cancel` | той, хто запитує | відкликає власний запит |

```js
const r = await client.contact.transfer('request', 'C1', 'the-code');

r.code();             // 1000 або 1001, коли він завершується асинхронно
r.transferStatus();   // 'pending'
r.transfer();
// { status, requestedBy, requestedAt, actingClient, actBy, expiryDate }
```

Власник дізнається про запит через [poll](poll.md) і відповідає `approve` або `reject`.
`op="query"` для контакту, у якого нічого не очікує, дає `2301`, а другий `request` для того, що
вже очікує, — `2300`.

**Коди відповіді:** `1000` / `1001`; `2201` (не ваш), `2202` (неправильний `authInfo`), `2300`,
`2301`, `2303`, `2304`.
