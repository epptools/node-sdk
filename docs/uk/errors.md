# Помилки

Кожен збій, який піднімає ця бібліотека, успадковує **`EppError`**, тож один `catch` покриває все, що
вона здатна кинути. Понад те, клас існує там, де відрізняється правильний наступний крок, — і більше
ніде. Класу для «трохи іншого відтінку того самого лікування» немає, бо систематика, за якою не можна
діяти, — це лише зайві назви для запам'ятовування.

```js
const { EppError } = require('@epptools/sdk');

try {
  await client.domain.create('example.com.ua', { years: 1, registrant: 'C1' });
} catch (err) {
  if (err instanceof EppError) { /* що завгодно з цієї бібліотеки */ }
  throw err;                    // будь-що інше — помилка у вашому власному коді
}
```

## Ієрархія

```
EppError
├── ConnectionError        транспорт: TLS, тайм-аут, кадрування
├── ConfigError            цей клієнт налаштований неправильно; кожен виклик падає однаково
├── ValidationError        аргументи цього виклику хибні; нічого не надіслано
└── CommandError           реєстр відмовив (код >= 2000)
    ├── AuthError                  2200
    ├── InsufficientFundsError     2104
    ├── AuthorizationError         2201, 2202
    ├── ObjectExistsError          2302
    ├── ObjectDoesNotExistError    2303
    ├── ObjectStatusError          2304, 2305
    ├── PolicyError                2306, 2308
    └── SessionError               2500, 2501, 2502
```

| Ловити | Коли піднімається | Коди | Що робити далі |
|---|---|---|---|
| `ValidationError` | значення в **цьому** виклику неможливо використати; **нічого не надіслано** | — | виправте аргументи. Наступний виклик може бути цілком добрим |
| `ConfigError` | сам клієнт налаштований неправильно: немає хоста, немає облікових даних, тайм-аут у хибних одиницях | — | виправте розгортання. Доти падає кожен виклик |
| `ConnectionError` | рукостискання TLS, тайм-аут під'єднання чи читання, кадрування, розсинхронізований потік | — | з'єднання закрито. Перепід'єднайтеся; для операції спершу прочитайте [правило невідомого підсумку](#коли-неможливо-сказати-чи-це-сталося) |
| `AuthError` | `login()` відхилено за обліковими даними | `2200` | перевірте clID і пароль. Не крутіть цикл: повторні збої призводять до блокування адреси-джерела |
| `InsufficientFundsError` | рахунок не може заплатити за цю операцію | `2104` | **зупиніть пакет**, поповніть, продовжте. Кожна наступна тарифікована команда падає так само |
| `AuthorizationError` | об'єкт існує, але не ваш, або `authInfo` хибний | `2201`, `2202` | не повторюйте з тими самими даними. Дістаньте правильний секрет трансферу або прийміть, що це не ваше |
| `ObjectExistsError` | уже зареєстровано або вже зайнято | `2302` | ім'я пішло. `err.subject()` каже, яке саме, коли команда несла кілька |
| `ObjectDoesNotExistError` | немає такого домену, ідентифікатора чи сервера імен | `2303` | застарілий ідентифікатор або друкарська помилка. Перечитайте власний запис, перш ніж повторювати |
| `ObjectStatusError` | поточний стан об'єкта це забороняє: `clientHold`, трансфер в очікуванні, хост, який ще прив'язаний | `2304`, `2305` | приберіть статус або зв'язок, потім надішліть ту саму команду знову |
| `PolicyError` | власні правила реєстру відмовляють цьому значенню | `2306`, `2308` | має змінитися сам запит. Повторювати немає сенсу |
| `SessionError` | сервер завершує сесію | `2500`, `2501`, `2502` | перепід'єднайтеся, увійдіть знову, потім повторіть команду — вона могла бути цілком доброю |
| `CommandError` | будь-який інший код відповіді 2000 або вище | усе інше | розгалужуйтеся за `err.eppCode`; див. [Коди відповіді](#коди-відповіді) |

Зіставлення коду з класом вирішується в одному місці, тож воно не може розійтися між командами.

## Поганий аргумент — це не погана конфігурація

`ValidationError` і `ConfigError` виглядають схоже й потребують протилежних реакцій — саме тому вони є
окремими класами, а не одним.

**`ValidationError` — про цей виклик.** Щось в аргументах неможливо використати, і бібліотека
відмовила ще до побудови кадру. Виправлення належить тому, хто зробив запит; наступний виклик, з
іншими аргументами, працює як слід.

| Піднімається через | Приклад |
|---|---|
| ключ опції, якого команда не знає | `secdns` замість `secDNS`, із названим найближчим відомим ключем |
| суму ціни, що не є простим десятковим числом | `'100,00'`, `'$100'` |
| змішування двох моделей серверів імен в одній команді | звичайне ім'я поруч з іменем із glue-адресами |
| одночасне встановлення й очищення `authInfo` домену | схема не вміє виразити обидва |
| запис DS без дайджеста, запис ключа без публічного ключа | |
| `removeAllDnssec()` поруч із названим прибиранням DNSSEC | у будь-якому порядку |
| створення контакту без пошти | RFC 5733 вимагає її |
| поле розкриття, якого не існує | `'addres'` |
| перейменування хоста | цей реєстр ігнорує `<host:chg>`; див. [Хости](hosts.md#хост-неможливо-перейменувати) |
| ціновий запит більш ніж на [двадцять позицій](balance.md#обмеження-у-20-записів) | |
| білдер, надісланий двічі | див. [Білдери](builders.md#білдер-надсилає-один-раз) |

**`ConfigError` — про розгортання.** Клієнт не здатен працювати взагалі, і кожен виклик падатиме
однаково, доки хтось не змінить налаштування. Це сповіщення для того, хто веде сервіс, а не відповідь
клієнтові.

| Піднімається через | Приклад |
|---|---|
| порожній `host` на `connect()` | |
| порожній `clid` чи `password` на `login()` | повідомлення каже, якого саме з двох бракує |
| пароль поза межами 6–128 символів | перевіряється до відкриття сокета |
| пароль довший за 16 символів там, де сервер не пропонує RFC 8807 | йому нікуди їхати; сервер відповів би голим `2001` |
| `connectTimeout` чи `readTimeout` менші за 1000 | це **мілісекунди**; значення, схоже на секунди, відхиляється, а не тихо піднімається |

Останнє варте того винятку, який воно піднімає. Прочитаний як мілісекунди, `readTimeout: 30` — це одна
тридцята секунди: строк спливає, поки реєстр ще працює, команду цілком могло бути виконано й
тарифіковано, а тайм-аут читання є остаточним — тож клієнт доповідає про збій операції, яка насправді
вдалася. Див. [Сесія](session.md#config).

```js
const { ValidationError, ConfigError } = require('@epptools/sdk');

try {
  await handleCustomerRequest(payload);
} catch (err) {
  if (err instanceof ValidationError) return reply(400, err.message);   // їхні вхідні дані
  if (err instanceof ConfigError) { pageTheOncall(err); return reply(503, 'temporarily unavailable'); }
  throw err;
}
```

## Збої транспорту: `ConnectionError`

Усе, що нижче за EPP, приходить як `ConnectionError`: рукостискання TLS, яке не пройшло перевірки,
тайм-аут під'єднання чи читання, кадр із неможливим префіксом довжини, некоректна чи обрізана
відповідь, відповідь, чий `clTRID` не збігається з надісланою командою.

У кожному випадку з'єднання закривається, і це навмисно. Потік, у якому зсуви поїхали, віддав би
відповідь попередньої команди наступному читанню — `renew('example2.com.ua')` повертає `1000` із датою
завершення `example1.com.ua`, обидва тарифіковані, а ваші записи хибні щодо обох. Закриття коштує вам
перепід'єднання; незакриття коштує вам правди.

Обрізаний кадр ніколи не розбирається в частковий `Response`, тож напівдоставлене створення не може
прочитатися назад як завершена тарифікована реєстрація.

Найчастіший на першому запуску — це перевірка сертифіката, і його виправлення — на сторінці
[Сесія](session.md#коли-рукостискання-не-вдається). Небезпечний — це тайм-аут читання **посеред операції**;
див. [Коли неможливо сказати, чи це
сталося](#коли-неможливо-сказати-чи-це-сталося).

## Чому відмовив реєстр: `CommandError`

Будь-який код відповіді 2000 або вище відхиляє проміс найконкретнішим класом для цього коду. Кожен із
них несе ті самі члени:

| Член | Тип | Що містить |
|---|---|---|
| `err.eppCode` | number | код відповіді EPP, напр. `2302` |
| `err.response` | `Response` \| `null` | повна розібрана відповідь — на ній працює кожен [аксесор](responses.md) |
| `err.message` | string | `EPP 2302: Object exists ('example.com.ua')` — код, власний текст реєстру і предмет, коли той його назвав |
| `err.isRetryable()` | boolean | чи могла б та сама команда, надіслана знову, спрацювати; див. [Повтори](#повтори) |
| `err.subject()` | string \| `null` | об'єкт, до якого був закид у реєстру, з першого `<extValue>` |
| `err.reasons()` | string[] | додатковий діагностичний текст, доданий реєстром |

```js
const { CommandError } = require('@epptools/sdk');

try {
  await client.domain.check(['example1.com.ua', 'b..com.ua', 'c.com.ua']);
} catch (err) {
  if (err instanceof CommandError) {
    err.eppCode;                       // 2005
    err.subject();                     // 'b..com.ua' — ЯКЕ саме з трьох
    err.reasons();                     // ['Invalid domain name syntax']
    err.response.extValues();          // те саме, з елементом і його простором імен
    err.response.svTRID();             // наводьте це в зверненні до підтримки
  }
}
```

`subject()` — це різниця між «одне з цих трьох імен відхилено» і знанням, яке саме. У команді, що несе
кілька об'єктів, відповідь усе одно лежить у відповіді; цей метод її читає.

### `AuthError`

Піднімається з `login()`, коли реєстр відповідає `2200`: clID або пароль хибний. Сесія так і не
відкрилася.

Він навмисно вузький. У вході можуть відмовити й тому, що рахунок на межі кількості сесій (`2502`),
що сервер закривається (`2501`), що оголошений вами сервіс не пропонується (`2307`), що це з'єднання
вже увійшло (`2002`), або через версію протоколу (`2100`) — кожна приходить власним класом із власним
виправленням. Називати їх усі помилкою автентифікації означає відправити вас міняти пароль, який ніколи
не був проблемою.

Не повторюйте `2200` у циклі. Повторні збої автентифікації з однієї адреси — саме те, що системи
захисту від вторгнень створені помічати.

### `InsufficientFundsError`

`2104`. Із запитом усе гаразд: рахунок не може за нього заплатити, і кожна наступна тарифікована
команда падає так само, доки баланс не поповнять.

Це той випадок, на якому пакет треба **зупинити**, а не пропустити. Цикл, що ставиться до нього як до
будь-якої іншої помилки, перемелює решту тисячі імен, породжуючи тисячу однакових збоїв, і ховає
єдиний факт, що мав значення.

```js
if (err instanceof InsufficientFundsError) { alertBilling(err.message); break; }
```

Перевіряйте рахунок перед прогоном через [`client.balance()`](balance.md#перед-пакетом) і пам'ятайте,
що це знімок: з того самого казана витрачають й інші сесії.

### `AuthorizationError`

`2201` — об'єкт належить іншому реєстратору. `2202` — наданий вами `authInfo` не збігається. Ніколи не
повторюйте з тими самими даними; з об'єктом нічого не зміниться.

Для трансферу `2202` означає, що код, який дав вам клієнт, хибний або його вже замінили. Попросіть
чинний, а не вгадуйте.

### `ObjectExistsError`

`2302`. Ім'я, ідентифікатор чи сервер імен уже зареєстровані. Повтор не зробить його вільним.

Між `check`, що сказав «доступно», і `create`, що каже `2302`, лежить справжня гонитва, а не помилка у
вашому коді: хтось інший зареєстрував це в проміжку. `err.subject()` називає те, на якому стався
збіг, коли команда несла кілька.

### `ObjectDoesNotExistError`

`2303`. Зазвичай застарілий ідентифікатор або друкарська помилка: ідентифікатор контакту, який ви
закешували, домен, який відтоді видалили. Перечитайте власний запис, перш ніж повторювати, і сприймайте
це як відповідь на питання («чи це ще існує?»), а не як несправність.

### `ObjectStatusError`

`2304` — власний статус об'єкта забороняє операцію, наприклад `clientDeleteProhibited` на видаленні або
`pendingTransfer`, що блокує решту. `2305` — забороняє зв'язок: хост, який ще використовує домен,
контакт, на який ще посилаються, домен із підпорядкованими хостами.

Та сама команда спрацює, щойно ви приберете те, що заважає, і саме це робить цю родину єдиною, де
«виправ і повтори» точно доречне.

### `PolicyError`

`2306` — правила реєстру відмовляють цьому значенню. `2308` — порушення політики керування даними.
Команда коректна, і надсилати її вам можна; реєстр каже «ні» саме цьому вмісту: номер ліцензії в зоні,
яка їх не приймає, період, якого зона не пропонує, glue-адреса на зовнішньому хості.

Повторювати немає сенсу, доки не зміниться сам запит. `err.reasons()` зазвичай каже, що змінити.

### `SessionError`

`2500`, `2501`, `2502`. Сервер завершує сесію — тайм-аут бездіяльності, перезапуск, ваш рахунок на
межі кількості сесій. Сама команда могла бути цілком доброю.

Перепід'єднайтеся, увійдіть знову і надішліть її ще раз. Це один із небагатьох по-справжньому
придатних до повтору збоїв, і `isRetryable()` повертає `true` для всіх трьох. На `2502` додайте
затримку: у рахунку вже стільки сесій, скільки йому дозволено, і грюкання у двері її не відчиняє.

## Повтори

```js
err.isRetryable()   // => boolean
```

True лише для збоїв про **момент**, а не про **запит**:

| Код | Клас | Чому повтор може спрацювати |
|---|---|---|
| `2400` | `CommandError` | реєстр не зміг завершити команду; із запитом усе було гаразд |
| `2500` | `SessionError` | сесія завершилася; спершу перепід'єднайтеся |
| `2501` | `SessionError` | сервер закривається; спершу перепід'єднайтеся |
| `2502` | `SessionError` | забагато сесій; перепід'єднайтеся після затримки |

Для всього іншого воно навмисно `false`. Повтор `2302` не зробить ім'я вільним, повтор `2104` не
заплатить за нього, а повтор `2306` не змінить політику реєстру. Цикл, що вважає кожен збій тимчасовим,
перетворює одну відмову на бан за частотою — а проти тарифікованої команди цикл, який не бачить цієї
різниці, і є тим, як за домен платять двічі.

```js
if (err instanceof CommandError && !err.isRetryable()) throw err;   // повтор не допоможе
```

Повторюйте із затримкою, що зростає — кількасот мілісекунд, потім секунда, потім дві, — і зі стелею на
кількість спроб. Для родини `2500` перед повтором перепід'єднайтеся й увійдіть: старого з'єднання
більше немає.

**`isRetryable()` нічого не каже про операцію, підсумку якої ви не знаєте.** Це інше питання, і в
нього нижче є власне правило.

## Вимкнення кидання винятків

`client.throwOnFailure(false)` припиняє відхиляти проміси на кодах відповіді 2000 і вище, тож
`response.code()` ви читаєте самі. Це перемикач на весь клієнт, `login()` усе одно відхиляє на
результаті, відмінному від `1000`, а `poll.drain()` усе одно відхиляє на відповіді, що не несе ні
сповіщення, ні порожньої черги. Повний розбір компромісу — у [Командах](commands.md#throwonfailure).

З вимкненим киданням ніщо не змушує вас подивитися на код. Це і є ціна: проігнорований
`response.code()` — це збій, якого ваша програма ніколи не помітить, тоді як необроблене відхилення
проміса — це те, що не пропустиш.

## Коди відповіді

Кожен код із RFC 5730, з константою, яку `ResultCode` для нього експортує, класом, яким він приходить,
і тим, що робити. Розгалужуйтеся за константою, а не за голим числом.

```js
const { ResultCode } = require('@epptools/sdk');
if (err.eppCode === ResultCode.OBJECT_EXISTS) { /* 2302 */ }
```

### Успіх — 1xxx

| Код | Константа | Означає | Що робити |
|---|---|---|---|
| `1000` | `SUCCESS` | зроблено | продовжуйте; об'єкт у тому стані, який ви просили |
| `1001` | `SUCCESS_PENDING` | прийнято, виконується поза сесією | **не надсилайте повторно.** Збережіть `svTRID` і стежте за [чергою](poll.md) щодо підсумку |
| `1300` | `SUCCESS_NO_MESSAGES` | черга порожня | припиніть спорожнення |
| `1301` | `SUCCESS_ACK_TO_DEQUEUE` | на вас чекає сповіщення | прочитайте, обробіть, тоді підтвердьте |
| `1500` | `SUCCESS_END_SESSION` | logout прийнято | сервер закриває з'єднання |

Жоден із них не відхиляє проміс. `1001` — той, на якому люди спотикаються: це ні збій, ні завершена
операція, а надсилання команди ще раз «про всяк випадок» і є тим, як домен реєструють і оплачують
двічі.

| `2001` | `COMMAND_SYNTAX_ERROR` | `CommandError` | кадр не є коректним за схемою | він не називає жодного поля, тож звіряйте кадр зі схемою; методи високого рівня цього не породжують |
| `2002` | `COMMAND_USE_ERROR` | `CommandError` | команда неправильна для цього стану, напр. другий `login` | виправте послідовність |
| `2003` | `REQUIRED_PARAMETER_MISSING` | `CommandError` | бракує чогось обов'язкового | повідомлення це називає; оновлення, яке не виражає жодної зміни, теж потрапляє сюди |

## Коли неможливо сказати, чи це сталося
Тайм-аут читання, обірване з'єднання або будь-який `ConnectionError` посеред `create`, `renew`,
`transfer`, `restore` чи `delete` лишає по-справжньому невідомий підсумок: **реєстр міг виконати
команду й списати з вас кошти ще до того, як відповідь загубилася.** Ця бібліотека не здатна
відрізнити одне від іншого, і ви за помилкою теж — загублена відповідь і команда, що ніколи не
дійшла, звідси виглядають однаково.

**Не повторюйте просто так.** Сліпий повтор — це те, як домен реєструють і оплачують двічі: перша
спроба вдалася, її відповідь померла на зворотному шляху, а друга або реєструє другий рік строку, або
стикається з вашою ж першою спробою. Списання є справжнім у будь-якому разі.

Натомість запитайте в реєстру, як воно є:

| Команда, що завалилася | Запитати | Повторювати лише якщо |
|---|---|---|
| `domain.create` | `domain.info(name)` | він відповідає `2303` — домену не існує |
| `domain.renew` | `domain.info(name)` і прочитати `expiryDate()` | дата завершення досі та, з якої ви починали |
| `domain.transfer('request')` | `domain.transfer('query', name)` | він відповідає `2301` — нічого не очікує |
| `domain.restore` | `domain.info(name)` і прочитати `rgpStatus()` | він досі в `redemptionPeriod` |
| `domain.delete` | `domain.info(name)` | домен усе ще на місці у своєму старому стані |
| `contact.create` | `contact.info(id)` | він відповідає `2303` |
| `host.create` | `host.info(name)` | він відповідає `2303` |

```js
const { ConnectionError, ObjectDoesNotExistError } = require('@epptools/sdk');

async function createOnce(client, name, opts) {
  try {
    return await client.domain.create(name, opts);
  } catch (err) {
    if (!(err instanceof ConnectionError)) throw err;   // відмова — це відповідь; це — ні

    // З'єднання зникло. Перепід'єднайтеся і запитайте в реєстру, як воно є.
    await client.connect();
    await client.login();
    try {
      const info = await client.domain.info(name);
      // Він існує. Створення відбулося, і з нас списали; запишіть це і НЕ надсилайте знову.
      await recordRegistration(name, info.expiryDate(), info.createdDate());
      return info;
    } catch (probe) {
      if (probe instanceof ObjectDoesNotExistError) return client.domain.create(name, opts);
      throw probe;   // усе ще неясно — вирішує людина, а не цикл
    }
  }
}
```

Три речі, які варто тримати в голові.

**`1001` не є невідомим підсумком.** Це певна відповідь: команду прийнято і вона виконується поза
сесією. Збережіть її `svTRID`, стежте за [чергою](poll.md) і зіставте сповіщення назад за цим
ідентифікатором. Повторне надсилання — та сама подвійна оплата з додатковими кроками.

**`contact.createAuto()` неможливо звірити за ідентифікатором**, бо ви його не обирали, і кожен виклик
карбує свіжий хендл. Сліпий повтор після загубленої відповіді лишає вас із двома контактами замість
одного. Звіряйте зі своїми записами — або беріть ідентифікатор, обраний вами, саме для того, щоб повтор
стикнувся з `2302`, а не вдався двічі.

**Збій, підсумку якого ви не можете встановити, заслуговує на оператора, а не на автоматичну другу
спробу.** Поставте його в чергу на розгляд разом із надісланим `clTRID` і об'єктом, якого він
стосувався. Це кілька ручних звірок на рік проти рахунку, якого ніхто не може пояснити.

## Пакет, що поводиться пристойно

Усе вищесказане у формі, якої більшість інтеграцій справді потребує:

```js
const {
  CommandError, ConnectionError, InsufficientFundsError, ObjectExistsError,
} = require('@epptools/sdk');

const taken = [];
const retryLater = [];
const needsReview = [];

for (const name of namesToRegister) {
  try {
    await client.domain.createBuilder(name)
      .years(1).registrant('C1').maxFee(quotedFor(name), 'UAH')
      .send();
  } catch (err) {
    if (err instanceof InsufficientFundsError) {
      // Це не проблема цього імені, а рахунку. Продовження дає той самий збій для кожного
      // наступного імені.
      alertBilling(err.message);
      break;
    }
    if (err instanceof ObjectExistsError) { taken.push(err.subject() || name); continue; }
    if (err instanceof ConnectionError) { needsReview.push(name); break; }   // підсумок невідомий
    if (err instanceof CommandError && !err.isRetryable()) throw err;        // повтор не допоможе
    retryLater.push(name);
  }
}
```

П'ять гілок, п'ять різних наступних кроків: зупинити прогін, записати ім'я як зайняте, віддати
операторові, здатися щодо нього або спробувати пізніше. У цьому й весь сенс ієрархії — кожен клас
існує тому, що рядок під ним відрізняється. Усе, що провалюється повз, — це збій, якого цей код не
передбачив, і він має дійти до людини, а не бути поглинутим перехопленням «усього підряд».
