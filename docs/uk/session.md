# Сесія

EPP-сесія — це TLS-сокет до реєстру на порт 700, `<greeting>`, яке сервер надсилає першим, `<login>`,
кілька команд і `<logout>`. Ця сторінка охоплює все це: налаштування, які відкривають сокет,
перевірки сертифіката, чотири сесійні команди, зміну пароля, блок безпеки RFC 8807 і те, як
журналювати кадри, не журналюючи облікових даних.

## Config

`Config` тримає налаштування з'єднання. Створіть його один раз і передайте в `Client`; змінювати його
згодом не передбачено.

```js
const { Client, Config } = require('@epptools/sdk');

const client = new Client(new Config({
  host: 'epp.registry.example',
  port: 700,
  clid: 'EXAMPLE',
  password: process.env.EPP_PASSWORD,
  caFile: '/etc/epp/registry-ca.pem',
  lang: 'uk',
  connectTimeout: 10000,
  readTimeout: 30000,
}));
```

| Поле | Типове значення | Що це |
|---|---|---|
| `host` | `''` | ім'я хоста реєстру |
| `port` | `700` | EPP-порт |
| `clid` | `''` | ваш ідентифікатор реєстратора |
| `password` | `''` | ваш EPP-пароль |
| `lang` | `'en'` | мова повідомлень реєстру про результат |
| `connectTimeout` | `10000` | строк на TLS-рукостискання, **у мілісекундах** |
| `readTimeout` | `30000` | строк на кожну відповідь, **у мілісекундах** |
| `verifyPeer` | `true` | перевіряти серверний сертифікат за `caFile` або системним сховищем |
| `verifyPeerName` | `true` | вимагати, щоб сертифікат збігався з `host` |
| `caFile` | `null` | шлях до PEM-файла з пакетом CA, який підписує **серверний** сертифікат |
| `clientCert` | `null` | шлях до PEM-файла вашого клієнтського сертифіката, для точки підключення зі взаємним TLS |
| `clientKey` | `null` | шлях до PEM-файла відповідного приватного ключа |
| `clientKeyPassphrase` | `null` | парольна фраза, якщо цей ключ зашифровано |
| `objUris` | `null` | сервіси об'єктів, які оголошувати під час входу; `null` означає «те, що запропонувало привітання» |
| `extUris` | `null` | сервіси розширень, які оголошувати під час входу; `null` означає те саме |
| `clTRIDPrefix` | `'NODEJS-SDK'` | префікс згенерованих клієнтських ідентифікаторів транзакцій |
| `registryExtUri` | `null` | простір імен ВЛАСНОГО об'єктного розширення цього реєстру; `null` читає його з привітання. Задавайте вручну лише для реєстру, чиє розширення назване не за зразком `…/registry-<версія>`. Хибне значення сервер не відхиляє, а ігнорує, тож дані мовчки не доходять. Див. [Команди](commands.md#власні-розширення-вашого-реєстру). |
| `registryBalanceUri` | `null` | те саме для розширення балансу облікового запису |
| `loginSecurity` | `true` | брати участь у розширенні Login Security (RFC 8807) там, де сервер його пропонує |

### Що буде, якщо поле задано неправильно

**`host`** — порожній хост ловить `connect()`, який кидає `ConfigError: Config: host must not be
empty` ще до того, як буде відкрито хоч якийсь сокет. Хост, який не резолвиться або відхиляє
з'єднання, виходить із `connect()` як `ConnectionError` із назвою адреси.

**`port`** — будь-що, крім EPP-порту на тому хості, або відхилить з'єднання, або завалить
TLS-рукостискання. Бібліотека говорить лише EPP поверх TLS; відкритого режиму немає, запасного
варіанта теж.

**`clid`, `password`** — обидва перевіряються в `login()` ще до складання кадру. Порожній будь-який
із них — це `ConfigError`, який називає, котрий саме. Неправильні облікові дані — це вже відмова з
боку сервера: код відповіді 2200, здійнятий як `AuthError`.

**Довжина `password`** — схемний тип `<pw>` із RFC 5730 дозволяє від 6 до 16 символів. Пароль поза
межами 6–128 — це `ConfigError` ще до підключення. Від 17 до 128 символів він може подорожувати лише
всередині блоку RFC 8807, тож якщо привітання сервера не оголошує це розширення, ви отримуєте
`ConfigError`, який каже саме це, — замість голого 2001 від сервера, який не називає жодного поля.

**`lang`** — має бути однією з оголошених сервером (`en`, `uk`, `ua`, `ru`; `ua` і `uk` — обидві
українська). Будь-що інше відхиляється під час входу з 2102 і здіймається як `CommandError`. Мова
впливає на текст `<msg>` реєстру і більше ні на що — коди відповіді однакові в кожній мові.

**`connectTimeout`, `readTimeout`** — мілісекунди, мінімум 1000, перевіряються під час створення
`Config`. Значення, яке не є додатним числом або менше за 1000, одразу кидає `ConfigError` з
повідомленням, яке підказує еквівалент у мілісекундах. Воно відхиляється, а не підіймається мовчки
до мінімуму, бо `readTimeout: 30`, прочитаний як мілісекунди, — це тридцята частка секунди: такий
короткий строк на create чи renew здається, поки реєстр іще працює, команду цілком могло бути
виконано і затарифіковано, а тайм-аут читання є остаточним — тож клієнт повідомив би про збій
операції, яка насправді вдалася.

**`caFile`, `clientCert`, `clientKey`** — вони читаються з диска, коли працює `connect()`. Шлях, якого
не існує, завалює підключення файловою помилкою (`ENOENT`) ще до відкриття сокета. Це проблема
розгортання, а не протоколу, і її навмисно не маскують під `ConnectionError`.

**`objUris`, `extUris`** — лишайте обидва `null`. Тоді клієнт оголошує рівно те, що запропонувало
привітання, тож сесію ніколи не буде відхилено з 2307 за запит сервісу, якого сервер не має.
Задавайте їх лише для того, щоб *звузити* оголошене. Порожній масив не оголошує в цій категорії
нічого, що вимикає відповідні розширення на всю сесію; базовий URI `epp-1.0` ніколи не надсилається
як сервіс об'єкта, бо він ним не є. Якщо привітання не перелічило жодного сервісу, клієнт
повертається до стандартних відображень об'єктів із RFC і до розширень, які публікує цей реєстр.

**`clTRIDPrefix`** — з'являється на початку кожного згенерованого клієнтського ідентифікатора
транзакції, тож ваші команди можна знайти у спільному журналі. Див.
[Команди](commands.md#клієнтські-ідентифікатори-транзакцій).

**`loginSecurity`** — задайте рівно `false`, щоб не брати участі в розширенні. Що ви цим втрачаєте —
див. [Безпека входу](#безпека-входу-rfc-8807).

## TLS

| Сценарій | Налаштування |
|---|---|
| `epp.registry.example:700` (сертифікат приватного CA) | задайте `caFile` на `.pem` із CA реєстру — **обов'язково** |
| Публічний сертифікат, якому довіряють браузери | типові значення (`verifyPeer: true`, `verifyPeerName: true`) |
| Розбіжність імені хоста в розробці | `verifyPeerName: false` |
| Точка підключення зі взаємним TLS | `clientCert` + `clientKey` (+ `clientKeyPassphrase`, якщо ключ зашифровано) |

Публічна точка підключення на `epp.registry.example:700` подає сертифікат, виданий **власним приватним
CA** реєстру, тож `caFile` має вказувати на пакет цього CA: системного сховища довіри він не
містить, і без нього рукостискання не вдається. Точка підключення — це строгий RFC EPP, і
клієнтський сертифікат їй **не потрібен**: автентифікація це clID плюс пароль поверх TLS, а на
вашому обліковому записі діє білий список IP.

З'єднання узгоджує щонайменше TLS 1.2, надсилає налаштований `host` як ім'я сервера SNI і перевіряє
ланцюжок сертифікатів, якщо ви цього не вимкнули.

### Коли рукостискання не вдається

Найчастіший збій під час першого запуску — це перевірка сертифіката, і виглядає він так:

```
ConnectionError: TLS/socket error on epp.registry.example:700 — certificate verify failed
```

Майже завжди це означає, що `caFile` не заданий або вказує не на той пакет. Перевірте його перш за
все:

```bash
openssl s_client -connect epp.registry.example:700 -CAfile /path/to/registry-ca.pem </dev/null
# "Verify return code: 0 (ok)" означає, що пакет правильний; будь-що інше — що ні.
```

Інші збої рукостискання і що вони означають:

| Повідомлення | Причина |
|---|---|
| `certificate verify failed` | неправильний або відсутній `caFile` |
| `Hostname/IP does not match certificate's altnames` | сертифікат правильний, але виданий на інше ім'я — перевірте `host`, перш ніж хапатися за `verifyPeerName: false` |
| `Connect to epp.registry.example:700 timed out after 10000 ms` | ніхто не відповів: фаєрвол, не той порт або вашій IP не дозволено діставатися до точки підключення |
| `ECONNREFUSED` | щось відповіло на адресі, але на тому порту ніхто не слухає |
| `ENOENT` під час підключення | `caFile` / `clientCert` / `clientKey` називає файл, якого немає |

**Не хапайтеся за `verifyPeer: false`.** Він прибирає повідомлення і лишає вас із тим, що ви
надсилаєте свій clID, свій пароль і кожен код авторизації трансферу тому, хто відповість на цій
адресі, без жодної змоги про це дізнатися. Якщо рукостискання не проходить перевірку, то пакет
неправильний — попросіть у реєстру чинний. `verifyPeerName: false` — це вужче послаблення
(правильний сертифікат, неправильне ім'я хоста), і в розробці воно інколи виправдане;
`verifyPeer: false` не виправданий ніде.

Вхід, відхилений з 2200 чи 2501, теж може бути проблемою, суміжною з TLS, а не неправильним паролем:
реєстр звіряє вихідну IP з вашим білим списком, а якщо для вашого облікового запису ввімкнено
прив'язку сертифіката, наданий клієнтський сертифікат має збігатися.

## Відкриття і закриття сесії

```js
await client.connect();     // TLS + читання <greeting>
await client.login();       // <login>
// … команди …
await client.logout();      // <logout>, у відповідь 1500; далі сервер закриває зв'язок
client.disconnect();        // закрити сокет локально
```

### `connect()`

```js
const greeting = await client.connect();
```

Відкриває TLS-сокет і читає `<greeting>`, яке сервер надсилає без запиту, повертаючи його як
[`Response`](responses.md). Викликайте його один раз на сесію — він читає рівно один кадр, тож
повторний виклик на відкритому з'єднанні спожив би відповідь, призначену чомусь іншому.

Саме з цим привітанням клієнт і входить. Воно зберігається в клієнті і доступне для читання згодом:

```js
client.greeting.value('svID');        // ім'я сервера
client.greeting.value('svDate');      // його годинник, його ж рядком
client.greeting.serviceObjUris();     // ['urn:ietf:params:xml:ns:contact-1.0', …]
client.greeting.serviceExtUris();     // ['urn:ietf:params:xml:ns:secDNS-1.1', …]
client.greeting.isGreeting();         // true
```

`client.greeting` дорівнює `null` до першого `connect()` або `hello()`.

### `hello()`

```js
const greeting = await client.hello();
```

Надсилає `<hello/>` і читає свіже `<greeting>`, яким відповідає сервер, замінюючи ним збережене. Дві
користі: перечитати меню сервісів без перепідключення і не дати сесії, яка інакше простоює,
закритися через бездіяльність. Ідентифікатора транзакції він не несе, бо `<hello>` не є командою.

### `login(newPassword = null)`

```js
const response = await client.login();
```

Надсилає `<login>` з вашим clID і паролем, версією протоколу `1.0`, вашим `lang` і сервісами з
привітання. Повертає відповідь на 1000 і відхиляється на будь-чому іншому:

| Код | Здіймається як | Значення |
|---|---|---|
| 2200 | `AuthError` | неправильний clID чи пароль, IP поза вашим білим списком або закритий контракт |
| 2002 | `CommandError` | на цьому з'єднанні вже виконано вхід |
| 2100 | `CommandError` | версію протоколу відхилено |
| 2102 | `CommandError` | запитаний `lang` не підтримується |
| 2307 | `CommandError` | оголошений вами сервіс не пропонується |
| 2501 | `SessionError` | в автентифікації відмовлено, і сервер закриває з'єднання |
| 2502 | `SessionError` | забагато одночасних сесій — сервер закриває з'єднання |

Кожен із цих випадків має власний спосіб усунення, і саме тому їх не називають усі помилкою
автентифікації: коли вам кажуть міняти пароль, який тут ні до чого, це коштує півдня. Зверніть
увагу, що `login()` відхиляється на результаті, відмінному від 1000, **незалежно від**
[`throwOnFailure`](commands.md#throwonfailure) — сесію, яка не відкрилася, немає сенсу розглядати.

Для цих двох кроків є скорочення:

```js
const client = await Client.connectAndLogin(config);   // статичний метод
```

Він створює клієнта, підключається і входить, повертаючи готового клієнта.

### `logout()` і `disconnect()`

```js
await client.logout();     // повертає код відповіді 1500
client.disconnect();
```

`logout()` завершує сесію ввічливо; сервер відповідає 1500, а потім закриває з'єднання.
`disconnect()` закриває сокет із вашого боку і позначає сесію як завершену. Він синхронний, не
приймає аргументів і його безпечно викликати будь-коли, зокрема коли нічого й не було підключено, —
саме тому йому місце в блоці `finally`. Після `disconnect()` той самий `Client` може знову викликати
`connect()`; транспорт відкривається чисто.

### Де ви зараз

```js
client.isConnected();   // чи сокет відкритий і справний
client.isLoggedIn();    // чи вдався login() і чи не спрацював відтоді logout()/disconnect()
```

Обидва — це локальний стан, а не звернення до сервера. `isConnected()` стає хибним тієї миті, коли
транспорт натрапляє на остаточну помилку — тайм-аут читання, закритий сокет, — тож це чесна перевірка
перед повторним використанням довгоживучого клієнта. Сесію, яку сервер розірвав між командами, ви
виявите на наступній команді як `ConnectionError`.

## Зміна пароля

```js
await client.login('new-secret-value');
```

Новий пароль подорожує в `<newPW>` поруч зі старим. **Зміна набуває чинності, лише якщо вхід
успішний**, і з наступної сесії ви маєте користуватися новим значенням — тож запишіть його туди, де
ваше розгортання тримає секрети, *перш ніж* вважати зміну завершеною. І старе, і нове значення
перевіряються за довжиною ще до того, як щось буде надіслано.

Два наслідки, які варто передбачити:

- Якщо новий пароль довший за 16 символів, його може нести лише блок RFC 8807, тож обліковий запис
  зможе автентифікуватися тільки там, де це розширення доступне. Якщо інше ваше ПЗ входить під тим
  самим обліковим записом там, де його не пропонують, це ПЗ почне падати. Реєстр надсилає
  попередження на тому самому вході, який встановлює такий пароль, — читайте `securityEvents()` у
  відповіді.
- Зміна через межу в 16 символів обробляється поелементно: переноситься лише те значення, якому це
  справді потрібно, тож заміна короткого пароля на довгий надсилає старий у `<pw>`, а новий — у
  `<loginSec:newPW>`.

## Безпека входу (RFC 8807)

Там, де сервер пропонує розширення Login Security, вхід несе невеликий блок, який ідентифікує цього
клієнта, а сервер відповідає всім, що він хоче бачити виправленим у цій сесії.

```js
for (const event of (await client.login()).securityEvents()) {
  console.warn(`[${event.level}] ${event.type}: ${event.text}`, event.exDate || '');
}
```

Кожна подія — це звичайний об'єкт із `text` плюс тими з цих атрибутів, які вона несла:

| Поле | Значення |
|---|---|
| `type` | `password`, `certificate`, `cipher`, `tlsProtocol`, `newPW`, `stat`, `custom` |
| `level` | `warning` або `error` |
| `name` | який саме набір шифрів, яка версія TLS або назва події `custom` |
| `exDate` | для `certificate`: точний момент завершення строку |
| `value`, `duration`, `lang` | так, як їх несе подія |

На здоровій сесії список порожній, тож ставтеся до будь-якого запису як до того, на що треба
зреагувати. Найчастіший випадок — клієнтський сертифікат, у якого добігає строк; альтернатива
дізнатися про це тут — дізнатися вранці того дня, коли він перестане працювати.

Сервер повертає їх **лише клієнтові, який надіслав блок розширення**, бо оголошення URI не є
свідченням уміння читати розширення: багато клієнтів формують свій `<svcExtension>`, просто
повертаючи вміст привітання. Саме тому блок іде навіть тоді, коли в ньому нічого не має подорожувати.
Він ідентифікує клієнта, і більше з нього нічого не береться:

```xml
<loginSec:userAgent>
  <loginSec:app>EppTools Node SDK 1.1.1</loginSec:app>
  <loginSec:tech>Node v20.11.0</loginSec:tech>
  <loginSec:os>linux</loginSec:os>
</loginSec:userAgent>
```

Задайте в конфігурації `loginSecurity: false`, щоб не брати в цьому участі. Тоді розширення
використовується лише там, де альтернативи немає, — для пароля, довшого за 16 символів, які може
нести базовий елемент `<pw>`, бо йому більше нікуди подітися. З вимкненим розширенням події безпеки
від сервера перестають до вас доходити.

## Журналювання із замаскованими секретами

```js
client.setLogger(console);            // або будь-який об'єкт із debug / info / warn
```

`setLogger()` повертає клієнта, тож він включається в ланцюжок. Що потрапляє в журнал:

| Рівень | Що |
|---|---|
| `debug` | кожен кадр в обох напрямках: `EPP >> request …`, `EPP << response …`, `EPP << greeting …` |
| `info` | один рядок на кожну успішну команду: `EPP result 1000 (svTRID=… clTRID=…)` |
| `warn` | той самий рядок для команди, яку реєстр відхилив |

Якщо в логера немає `info` чи `warn`, бібліотека переходить на `log`. Якщо немає `debug`, кадри не
журналюються взагалі — і це правильне типове значення для промислової експлуатації, де вам потрібні
рядки результатів, а не корисне навантаження.

**Кадри маскуються, перш ніж дістатися логера.** Вміст будь-якого елемента `<pw>` чи `<newPW>`, з
будь-яким префіксом простору імен, замінюється на `***`. Це охоплює пароль входу, `<newPW>` під час
зміни, `<loginSec:pw>` із RFC 8807 і `<pw>` усередині кожного блоку `<authInfo>` — тобто код
авторизації трансферу, ті облікові дані, які дають будь-якому реєстраторові змогу забрати у вас
домен.

Маскування — це поведінка бібліотеки на її власному шляху журналювання. Якщо ви серіалізуєте `Frame`
самотужки через `toXml()` і запишете рядок у журнал, його ніщо не замаскувало — виконайте це
затирання самі, перш ніж воно потрапить на диск або у звернення до підтримки.

## Транспорт, якщо він вам потрібен

`Client` приймає необов'язкові з'єднання і логер, і саме так у тестах підміняють транспорт:

```js
const { Client, Connection } = require('@epptools/sdk');

const client = new Client(config, new Connection(config), console);
```

`Connection` — це шар кадрування з RFC 5734 і більше нічого; семантики EPP він не знає:

| Метод | Що робить |
|---|---|
| `open()` | відкриває TLS-сокет; завершується, коли рукостискання завершено |
| `isOpen()` | чи сокет живий і чи не зафіксовано остаточної помилки |
| `writeFrame(xml)` | пише один кадр із його 4-байтовим префіксом довжини (big-endian) |
| `readFrame()` | повертає тіло наступного повного кадру рядком |
| `close()` | знищує сокет |

Кадрування рахує **байти**, а не символи, тож кирилиця та IDN-навантаження кадруються правильно. Три
обмеження бережуть процес: кадр, який заявляє понад 1 МіБ, відхиляється, непрочитані дані понад 4 МіБ
закривають з'єднання, а кожен `readFrame()` несе власний строк `readTimeout`.

Цей останній строк навмисно стосується читання, а не є таймером бездіяльності сокета: EPP-сесії, у
якій немає команди в польоті, нічого отримувати, і таймер бездіяльності знищив би цілком здорову.
**Тайм-аут читання є остаточним.** Відповідь, яка прийшла після строку, розсинхронізувала б потік —
наступне читання повернуло б відповідь на попередню команду, — тож замість цього з'єднання
закривається. Що це означає для create чи renew, написано в
[Помилках](errors.md#коли-неможливо-сказати-чи-це-сталося).
