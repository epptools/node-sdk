# Відповіді

Кожна команда повертає `Response`: розібрану відповідь із іменованим аксесором для всього, що реєстр
може надіслати назад. Ви ніколи не звертаєтесь до розібраного документа за рядком, який довелося
вгадати, і ніколи не торкаєтесь XML, якщо самі цього не хочете.

Пошук елементів іде за **локальним іменем і URI простору імен**, ніколи за префіксом, тож реєстр,
який пише свої префікси інакше, не ламає жодного аксесора на цій сторінці.

Наскрізно діють два правила, і саме вони коштують грошей, коли їх порушено:

- **Дати — це власний рядок реєстру** — `2027-04-01T09:15:00Z` — ніколи не `Date`. Реєстр вирішує, на
  який календарний день припадає продовження; переформатування через місцевий часовий пояс — це
  саме той шлях, яким клієнт зрештою показує попередній день і продовжує реєстрацію відносно нього.
- **Гроші — це точний десятковий рядок** — `'100.00'` — ніколи не число. `0.1 + 0.2` у двійковій
  рухомій комі не дорівнює `0.3`, і баланс, підсумований так, поступово розходиться. Використовуйте
  бібліотеку десяткової арифметики або цілі числа в найменших одиницях валюти.

## Результат

| Аксесор | Що повертає | Коли у відповіді цього немає |
|---|---|---|
| `code()` | код відповіді EPP числом: 1000, 1001, 2303 … | `0` — його не використовує жодна відповідь EPP, тож він означає «цей кадр не ніс результату», як-от привітання |
| `isSuccess()` | `true` для будь-якого коду від 1000 до 1999 | `false` |
| `isPending()` | `true` рівно для 1001 | `false` |
| `isGreeting()` | `true`, коли кадр є `<greeting>`, а не `<response>` | `false` |
| `message()` | зрозумілий людині текст `<result><msg>` | `null` |
| `messageLang()` | мова цього тексту: `'en'`, `'uk'`, `'ua'` чи `'ru'` | `null` |
| `statuses()` | статуси об'єкта, напр. `['ok']` або `['clientHold', 'clientUpdateProhibited']` | `[]` |
| `errorReasons()` | додатковий текст `<reason>`, який реєстр додав до відмови | `[]` |
| `extValues()` | блоки `<extValue>` повністю — див. нижче | `[]` |
| `clTRID()` | ідентифікатор транзакції, надісланий вашою командою, повернутий назад | `null` |
| `svTRID()` | власний ідентифікатор транзакції реєстру | `null` |

```js
const r = await client.domain.info('example.com.ua');
r.code();        // 1000
r.statuses();    // ['ok']
r.svTRID();      // збережіть це поруч із доменом
```

### `extValues()`

```js
r.extValues();
// [{ element, namespace, text, values, xml, reason, lang }, …]
```

`errorReasons()` дає вам сам лише текст, з яким нічого не зробиш: він каже, що щось відхилено, але
ніколи — котре з п'яти надісланих вами імен. `extValues()` каже котре. Саме так EPP вказує на
проблемну частину запиту, і кожен запис несе:

| Поле | Що містить |
|---|---|
| `element` | локальне ім'я елемента, до якого реєстр має претензію, напр. `name` |
| `namespace` | URI простору імен цього елемента або `''` |
| `text` | його символьні дані — для звичайного випадку, листка на кшталт `<domain:name>bad..name</domain:name>`, це і є відповідь |
| `values` | його нащадки за локальними іменами, для випадку, коли елемент є контейнером, а не листком |
| `xml` | елемент, серіалізований назад так, як він прийшов, якщо ви волієте розібрати його самі |
| `reason` | текст `<reason>` поруч із ним |
| `lang` | мова цієї причини |

Контейнер приходить із порожнім `text`, бо власних символьних даних контейнер не має — для цього і є
`values` та `xml`. Сервер також може перенести сюди дані, які не міг повернути у звичайний спосіб
(RFC 9038), а вміст `<value>` подається як дані і ніколи не інтерпретується.

## Ідентичність об'єкта

Ці аксесори відповідають для кожного об'єкта — домену, хоста чи контакту.

| Аксесор | Що повертає | Коли у відповіді цього немає |
|---|---|---|
| `objectName()` | доменне ім'я, ім'я хоста або **ідентифікатор** контакту | `null` |
| `roid()` | власний ідентифікатор об'єкта в реєстрі | `null` |
| `sponsor()` | `clID` реєстратора, якому об'єкт належить зараз | `null` |
| `registrarOfRecord()` | ідентифікатор, який WHOIS і RDAP реєстру публікують як реєстратора | `null` |
| `createdBy()` | `crID` — хто його створив | `null` |
| `createdDate()` | `crDate`, власним рядком реєстру | `null` |
| `updatedBy()` | `upID` — хто змінював його востаннє | `null`, якщо його ніколи не змінювали |
| `updatedDate()` | `upDate` | `null`, якщо його ніколи не змінювали |
| `authInfo()` | код авторизації трансферу об'єкта, `<authInfo><pw>` | `null`, коли реєстр його не віддав |

`objectName()` читає безпосереднього нащадка блоку об'єкта, і це має значення на контакті: пошук
елемента `<name>` по всьому документу спершу знайшов би повне ім'я особи всередині поштового блоку,
а подання цього назад як ідентифікатора притягує 2303. На `contact.createAuto()` це те місце, де
з'являється згенерований реєстром ідентифікатор, і єдине місце, де він з'являється, — збережіть
його.

`sponsor()` і `registrarOfRecord()` — це не одна й та сама сторона. `sponsor()` називає обліковий
запис, якому належить об'єкт, і у вашій власній ієрархії реселерів це ви; `registrarOfRecord()` —
це те, що реєстр публікує для всього світу, і для реселера це хтось інший.

`updatedBy()` у парі з `updatedDate()` — це те, з чим ви звіряєтесь: зміна, якої ви не робили,
прийшла з боку реєстру або від дії підтримки, а не з вашої системи.

**`authInfo()` — це живі облікові дані.** Він присутній лише для реєстратора-власника і лише на
`info`, який його запитав. Будь-хто, у кого він є, може перевести домен до іншого реєстратора.
Ніколи не журналюйте його, ніколи не кладіть його у звернення до підтримки і змініть його після
того, як передали клієнтові.

## Домен

| Аксесор | Що повертає | Коли у відповіді цього немає |
|---|---|---|
| `expiryDate()` | `exDate` рівно так, як його написав реєстр | `null` |
| `registrant()` | ідентифікатор контакту реєстранта | `null` |
| `contacts()` | контакти за ролями: `{ admin: ['c-1'], tech: ['c-1', 'c-2'] }` | `{}` |
| `contactsFor(role)` | ідентифікатори в одній ролі, зіставлені без урахування регістру | `[]` |
| `adminContacts()` | адміністративні контакти | `[]` |
| `techContacts()` | технічні контакти | `[]` |
| `billingContacts()` | білінгові контакти | `[]` |
| `allContacts()` | кожен ідентифікатор, приєднаний у будь-якій якості, включно з реєстрантом, без повторів | `[]` |
| `nameservers()` | делегування, іменами в нижньому регістрі | `[]` |
| `nameserverAddresses()` | вбудовані glue-адреси за іменами серверів імен | `{}` |
| `subordinateHosts()` | об'єкти хостів, що живуть **під** цим доменом | `[]` |
| `transfer()` | трансфер повністю — див. нижче | `null` |
| `transferStatus()` | `trStatus`, напр. `'pending'` або `'serverApproved'` | `null` |
| `transferDate()` | коли об'єкт востаннє змінив власника | `null`, якщо не змінював ніколи |
| `rgpStatus()` | статуси викупу, напр. `['redemptionPeriod']` (RFC 3915) | `[]` |
| `license()` | номер торгової марки або ліцензії з власного розширення реєстру | `null` |
| `dsRecords()` | DS-записи DNSSEC (RFC 5910) | `[]` |
| `keyRecords()` | записи ключів DNSSEC | `[]` |
| `isSigned()` | `true`, коли є хоч один DS-запис або запис ключа | `false` |
| `prices()` | підказки про ціну продовження та відновлення, за операціями | `{}` |
| `priceChannel()` | непрозорий ідентифікатор рядка каталогу цін, за яким тарифікується цей домен | `null` |

`contacts()` навмисно не містить реєстранта: це окремий елемент із власним значенням, тож читайте
його з `registrant()`. `contactsFor()` зіставляє роль без урахування регістру, бо реєстри непослідовні
щодо `tech` проти `Tech`, а точний пошук повідомляє «технічного контакту немає» для домену, у якого
він є. Порожній список — це законна відповідь: скрізь обов'язковий лише реєстрант.

`nameservers()` повертає імена так, як їх виразив реєстр, — чи то через `<domain:hostObj>`
(посилання на об'єкт хоста), чи то через `<domain:hostAttr>` (ім'я, вбудоване разом зі своїми
glue-адресами). Читання лише однієї з двох моделей повертає порожній список для реєстру, який
користується іншою, а це читається як «у цього домену немає серверів імен».
`nameserverAddresses()` заповнюється лише для вбудованої моделі:

```js
r.nameservers();
// ['ns1.example.com.ua', 'ns2.example.com.ua']

r.nameserverAddresses();
// { 'ns1.example.com.ua': [{ ip: '203.0.113.1', version: 'v4' },
//                          { ip: '2001:db8::1',  version: 'v6' }] }
```

Порожній результат `nameserverAddresses()` **не** означає, що домен не делеговано. Для реєстру, який
відповідає посиланнями на об'єкти хостів, ви отримуєте тут імена і дістаєте адреси через
`host.info()` для кожного імені.

`subordinateHosts()` має значення перед видаленням: реєстр відмовляється видаляти домен, поки під ним
живуть об'єкти серверів імен. Спершу перевірте список і приберіть їх або переспрямуйте.

```js
r.transfer();
// { status: 'pending',
//   requestedBy: 'ACME', requestedAt: '2026-08-10T09:00:00Z',
//   actingClient: 'EXAMPLE', actBy: '2026-08-15T09:00:00Z',
//   expiryDate: '2028-01-15T00:00:00Z' }
```

Сам лише `transferStatus()` каже, що трансфер очікує, але не каже, чий він і скільки часу у вас
лишилося. `actBy` — це строк, після якого реєстр вирішує за вас.

```js
r.dsRecords();   // [{ keyTag: 12345, alg: 8, digestType: 2, digest: 'ABCD…' }]
r.keyRecords();  // [{ flags: 257, protocol: 3, alg: 8, pubKey: 'AwEAA…' }]
```

`prices()` повертає `{ renewal: { value: '90.00', currency: 'UAH' }, … }` — підказки реєстру про ціну
на `info`, за операціями. Щоб отримати котирування, за яким можна діяти до покупки, спитайте запитом
тарифу в `domain.check()` і прочитайте [`fees()`](#check-і-гроші). `priceChannel()` стосується домену,
а не зони: домен, зареєстрований давно, може сидіти на іншому рядку каталогу, ніж той, яким
скористалася б нова реєстрація в тій самій зоні.

## Хост

| Аксесор | Що повертає | Коли у відповіді цього немає |
|---|---|---|
| `hostAddresses()` | glue-адреси хоста: `[{ ip: '203.0.113.10', version: 'v4' }, …]` | `[]` |

Glue-адреси має лише хост **усередині** зони, яку він обслуговує. Для зовнішнього сервера імен
реєстр не повертає жодної, і це нормально, а не відсутність відповіді. Відсутній атрибут версії
читається як `v4` — це власне типове значення схеми хостів.

Цей аксесор стосується самого об'єкта хоста. Вбудовані glue-адреси домену — це
`nameserverAddresses()`, який тримає кожну адресу разом із сервером імен, якому вона належить.

## Контакт

| Аксесор | Що повертає | Коли у відповіді цього немає |
|---|---|---|
| `postalInfo()` | поштові адреси за формами: `int` і `loc` | `{}` |
| `email()` | адреса електронної пошти контакту | `null` |
| `voice()` | номер телефону у формі EPP `+CC.NNNNNNNNN` | `null` |
| `fax()` | номер факсу, та сама форма | `null` |
| `disclose()` | налаштування розкриття — див. нижче | `null`, коли контакт його не несе і діє сама лише політика реєстру |

```js
r.postalInfo();
// { int: { name: 'ACME LLC', org: '', street: ['1 Example St'],
//          city: 'Kyiv', sp: '', pc: '01001', cc: 'UA' },
//   loc: { name: 'ТОВ АКМЕ',  org: '', street: ['вул. Прикладна, 1'],
//          city: 'Київ', sp: '', pc: '01001', cc: 'UA' } }
```

`int` — це ASCII-форма, яку приймає кожен реєстр і яка переживає друк, надсилання поштою і читання
системою, що не знає кирилиці. `loc` — це локальне письмо, адреса так, як її справді написав
реєстрант. Контакт може нести одну з форм або обидві, а частини, яких реєстр не надіслав,
повертаються як `''`, а не відсутніми, тож їх можна читати, не захищаючи кожне звернення.

```js
r.disclose();
// { flag: false, elements: ['email', 'voice', 'name:int'] }
```

`flag` — це і є весь сенс списку: `true` означає, що перелічені елементи **можна** публікувати,
`false` — що їх треба приховати. Елементи, яких у списку немає, отримують протилежне до прапорця,
тож читання списку без прапорця вивертає налаштування приватності навпаки. Поля, які існують по
одному на кожну поштову форму, подаються як `name:int`, `addr:loc` тощо.

## Check і гроші

| Аксесор | Що повертає | Коли у відповіді цього немає |
|---|---|---|
| `availability()` | уся відповідь check: `{ 'example.com.ua': true, 'taken.com.ua': false }` | `{}` |
| `isAvailable(name)` | `true` чи `false` для одного імені, зіставленого без урахування регістру | **`null`** — у відповіді про нього не сказано нічого |
| `unavailableReason(name)` | чому воно недоступне, напр. `'In use'` або `'Reserved'` | `null`, коли воно доступне або коли реєстр не назвав причини |
| `fees()` | таблиця цін за RFC 8748, за іменами — див. нижче | `{}` |
| `feeFor(name, operation, years = 1)` | одне котирування, точним десятковим рядком | `null` |
| `feeClass(name)` | клас тарифу в реєстрі, напр. `'premium'` або `'standard'` | `null` |
| `isPremium(name)` | `true`, коли ім'я тарифікується поза стандартним переліком | `false` |
| `chargedFee()` | скільки змінна команда справді списала: `{ currency: 'UAH', fee: '100.00' }` | `null` |
| `feeAmount()` | сама лише сума з цього | `null` |
| `feeCurrency()` | сама лише її валюта | `null` |
| `balance()` | блок облікового запису: `{ creditLimit, balance, availableCredit }` | `null`, коли відповідь не є відповіддю про баланс |
| `creditLimit()` | ваша кредитна лінія | `null` |
| `currentBalance()` | ваш поточний баланс | `null` |
| `availableCredit()` | скільки ви ще можете витратити: баланс плюс кредитна лінія, якщо вона є | `null` |

**`isAvailable()` повертає три речі, а не дві.** `null` означає, що відповідь не несла присуду щодо
цього імені взагалі, а це не те саме, що «зайнято», і не має виглядати так само для рядка, який його
реєструє. Порівнюйте з `true` явно:

```js
if (check.isAvailable(name) !== true) return;    // охоплює і false, І null
```

```js
const r = await client.domain.check(['example.com.ua'], { create: [1, 2, 5] }, 'UAH');

r.fees();
// { _currency: 'UAH',
//   'example.com.ua': {
//     avail: true,
//     reason: null,
//     class: 'premium',                      // є лише тоді, коли реєстр його вказав
//     commands: { create: { years: 1, fee: '100.00' } },
//     periods: [ { op: 'create', years: 1, fee: '100.00' },
//                { op: 'create', years: 2, fee: '195.00' },
//                { op: 'create', years: 5, fee: '480.00' } ] } }

r.feeFor('example.com.ua', 'create', 5);   // '480.00'
```

`_currency` — це валюта, у якій котирується вся таблиця. Для окремого імені `avail: false` разом із
`reason` — це спосіб реєстру сказати, що він не може котирувати це ім'я (зона, яку він не
обслуговує, або валюта, у якій він не котирує), і це окрема відповідь від того, що ім'я недоступне.

`commands` містить по одному запису на операцію, а `periods` містить кожне котирування. Запит однієї
операції на кількох періодах повертає кілька котирувань з однаковою назвою операції, тож для
конкретної цифри користуйтеся `feeFor()`, а не звертайтеся до `commands`. `transfer` і `restore` є
однорічними операціями, скільки б років ви не запитали; читайте їх на 1.

`isPremium()`, який повертає `false`, не є обіцянкою стандартної ціни — він означає, що у відповіді
не оголошено особливого класу. Тарифікуйте з `fees()` і повторюйте суму на самій змінній команді,
щоб реєстр міг відмовити, а не взяти зайве. Суми, наведені тут, ілюстративні, а не тариф реєстру.

`chargedFee()`, `feeAmount()` і `feeCurrency()` читають відлуння на успішній змінній команді, яка
несла погодження тарифу, — суму, яку вам справді виставили, і саме її треба звіряти, а не ту, яку ви
котирували.

Аксесори балансу працюють на відповіді `client.balance()`; усі три суми — точні десяткові рядки.
Див. [Баланс](balance.md).

## Poll

| Аксесор | Що повертає | Коли у відповіді цього немає |
|---|---|---|
| `messageId()` | ідентифікатор, який передається в `poll.ack()` | `null` — у цій відповіді немає повідомлення |
| `messageCount()` | скільки повідомлень лишається в черзі | `0` |
| `queueMessage()` | **текст повідомлення** з `<msgQ><msg>` | `null` |
| `queueMessageLang()` | мова цього повідомлення: `'uk'`, `'ru'` чи `'en'` | `null` |
| `queueDate()` | коли повідомлення потрапило в чергу | `null` |
| `pendingActionData()` | результат операції, обробленої офлайн, — див. нижче | `null` |

`queueMessage()` — це **не** `message()`. `message()` повертає банер результату команди («Command
completed successfully; ack to dequeue»), однаковий у кожній відповіді poll. Читання повідомлення
через `message()` віддає вам цей сталий рядок, тоді як справжній вміст губиться, — а підтвердження
потім знищує його в реєстрі назавжди.

```js
r.pendingActionData();
// { object: 'example.com.ua',
//   success: true,
//   clTRID: 'NODEJS-SDK-20260816103012-24191-0003',
//   svTRID: 'SRV-19700101103512-24191-00007',
//   date:   '2026-08-16T10:31:00Z' }
```

Саме так відкладена команда звітує про себе (RFC 5731 §3.3, RFC 5733 §3.3). Ви надсилаєте create,
отримуєте 1001 зі `svTRID`, а відповідь надходить пізніше в чергу. Три речі про її читання:

- **Лише `success` каже, чи все спрацювало.** Навколишній код відповіді 1301 означає «ось
  повідомлення», а не «ваша операція вдалася». Читання коду відповіді замість цього робить кожну
  відповідь poll схожою на успіх.
- **`svTRID` — це ідентифікатор початкової команди**, а не цієї відповіді poll. Зіставте його з тим,
  який ви зберегли разом із 1001, щоб зрозуміти, про яку саме відкладену операцію йдеться. Poll —
  це черга; повідомлення на її початку не обов'язково стосується останнього, що ви робили.
- `date` — це коли дія завершилася, а не коли ви опитали чергу.

Повний цикл, зокрема чому підтвердження має йти після вашої обробки, а не перед нею, — у
[Poll](poll.md).

## Безпека сесії та привітання

| Аксесор | Що повертає | Коли у відповіді цього немає |
|---|---|---|
| `securityEvents()` | попередження RFC 8807 про цю сесію | `[]` — здорова сесія |
| `serviceObjUris()` | простори імен об'єктів, які оголошує привітання | `[]` |
| `serviceExtUris()` | простори імен розширень, які оголошує привітання | `[]` |

```js
for (const event of (await client.login()).securityEvents()) {
  // { type, level, text, name?, exDate?, value?, duration?, lang? }
  alert(event.level, event.type, event.text, event.exDate);
}
```

`type` — це одне з `password`, `certificate`, `cipher`, `tlsProtocol`, `newPW`, `stat` чи `custom`;
`level` — це `'warning'` або `'error'`. Оскільки на здоровій сесії список порожній, будь-який запис
є тим, на що треба зреагувати: сертифікат, у якого строк добігає за три тижні, приходить сюди як
`type: 'certificate'` з датою в `exDate`. Див. [Сесія](session.md#безпека-входу-rfc-8807).

Два сервісні аксесори читають привітання, а привітання — це те, що повертають `connect()` і
`hello()`.

## Прямий доступ

| Аксесор | Що повертає | Коли у відповіді цього немає |
|---|---|---|
| `value(local)` | перший елемент будь-де з таким локальним іменем, обрізаний з боків | `null` |
| `values(local)` | кожен елемент із таким локальним іменем, обрізаний з боків | `[]` |
| `resData()` | елемент `<resData>` розібраного дерева | `null` |
| `root()` | корінь розібраного дерева | корінь на розібраному кадрі є завжди |
| `raw()` | XML відповіді рівно так, як він прийшов | кадр так, як його прочитано |
| `Response.fromXml(xml)` | розбирає кадр у `Response` (статичний метод) | кидає `ConnectionError` на будь-чому, що не є одним коректним деревом елементів |

```js
r.value('exDate');     // елемент, якого не охоплюють іменовані аксесори
r.values('hostObj');   // усі такі елементи
```

Це запасний вихід для розширення, до якого в цій бібліотеці немає аксесора, і спосіб прочитати
[власний кадр](commands.md#власні-кадри), який ви зібрали самі. Обидва зіставляють за локальним
іменем і не зважають на простори імен, тож `value('name')` знаходить перший `<name>` у порядку
документа, хай який у нього префікс, — надавайте перевагу іменованому аксесору щоразу, коли він є,
бо він знає, *котрий* саме елемент йому потрібен.

`Response.fromXml()` відхиляє обрізаний кадр, а не повертає часткове дерево, і саме це не дає
напівдоставленому create прочитатися як завершена реєстрація, за яку є що списати.
