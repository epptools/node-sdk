# Poll — черга повідомлень

Усе, що стається з вашими об'єктами поза вашим власним потоком команд, доходить до вас через
чергу повідомлень, окрему для кожного реєстратора: запитаний кимось трансфер, результат
відкладеної (`1001`) операції, попередження про завершення терміну реєстрації, повідомлення про
видалення, подія низького балансу. Читаєте ви її командою EPP `<poll>` (RFC 5730).

`client.poll` має три методи.

| Метод | Що йде в канал передачі |
|---|---|
| `request()` | `<poll op="req"/>` |
| `ack(messageId)` | `<poll op="ack" msgID="…"/>` |
| `drain(handler, limit = 0)` | цикл `req` / обробка / `ack` поверх обох |

Кожен повертає `Promise<Response>`, окрім `drain()`, який розв'язується кількістю оброблених
сповіщень.

**Спорожняйте свою чергу регулярно.** Реєстр зберігає повідомлення близько місяця; вам нічого не
надсилається саме собою, а черга, якої ніхто не читає, — це запит на трансфер, на який ніхто не
відповів. Кожен приклад нижче припускає підключений `client`, який уже виконав вхід, — див.
[Швидкий старт](quickstart.md).

---

## request

```js
request()   // => Promise<Response>
```

Запитує повідомлення з голови черги. Читання його не видаляє: те саме сповіщення повернеться на
наступному `request()`, доки ви його не підтвердите, тож клієнт, роботу якого перервано, ніколи не
втрачає події.

Тут важать два коди успіху:

| Код | Значення |
|---|---|
| `1301` | сповіщення очікує, і воно є в цій відповіді |
| `1300` | черга порожня; відповідь не несе сповіщення |

```js
const notice = await client.poll.request();

if (notice.code() === 1300) {
  // Нічого не очікує.
} else {
  notice.messageId();        // '10021' — ідентифікатор, який передають у ack()
  notice.messageCount();     // 3 — скільки лишається, включно з цим
  notice.queueMessage();     // 'Transfer requested.' — текст СПОВІЩЕННЯ
  notice.queueMessageLang(); // 'uk' | 'ru' | 'en'
  notice.queueDate();        // '2026-08-16T09:15:00Z' — коли його поставлено в чергу
}
```

**Читайте сповіщення через `queueMessage()`, а не через `message()`.** Це різні елементи.
`message()` повертає банер результату команди — «Command completed successfully; ack to dequeue» —
однаковий у кожній poll-відповіді й такий, що нічого не каже про подію. Цикл, який читає
`message()`, віддає вам цей сталий рядок, тоді як справжній вміст лишається непрочитаним, а `ack`,
що йде слідом, знищує його в реєстрі.

`messageCount()` дорівнює `0` для порожньої черги, тож він не дає відрізнити «порожньо» від
«лишилося одне»: користуйтеся кодом.

**Коди відповіді:** `1300`, `1301`.

## ack

```js
ack(messageId)   // => Promise<Response>
```

Підтверджує одне сповіщення за його ідентифікатором, що **назавжди видаляє його в реєстрі**.
Повернути його неможливо, і повторно воно не доставляється.

```js
const notice = await client.poll.request();

if (notice.messageId() !== null) {
  await store(notice.queueMessage(), notice.pendingActionData());   // СПОЧАТКУ обробка
  const after = await client.poll.ack(notice.messageId());          // потім підтвердження
  after.messageCount();   // скільки лишилося
}
```

Відповідь на `ack` — це `1301`, поки лишаються повідомлення (з оновленою кількістю, а в цьому
реєстрі — і з ідентифікатором наступного), або `1300`, щойно черга порожня. Тіла сповіщення вона
не несе ніколи; це робить лише `req`.

**Старе сповіщення все одно можна підтвердити.** Термін зберігання стосується доставлення, а не
вашого підтвердження: щойно повідомлення вам видано, воно лишається підтверджуваним, навіть якщо
місяць спливе, поки ви його тримаєте. Прочитати, зберегти, підтвердити пізніше — це підтримуваний
порядок.

**Коди відповіді:** `1300`, `1301`.

## drain

```js
drain(handler, limit = 0)   // => Promise<number>
```

Читає чергу до кінця, передаючи кожне сповіщення вашому обробнику й підтверджуючи його **після**
того, як обробник розв'яжеться.

```js
const processed = await client.poll.drain(async (notice) => {
  await store(notice.queueMessage(), notice.pendingActionData());
});
```

`limit`, що дорівнює `0`, означає «доки черга не спорожніє». Передайте число, щоб зупинитися після
відповідної кількості: черга, яка наповнюється швидше, ніж ви її спорожняєте, інакше тримала б
виклик запущеним нескінченно, а це погано пасує будь-чому, що працює за таймером.

### Уся суть — у порядку

`ack` іде останнім, і саме заради цього порядку цей помічник існує.

`ack` назавжди видаляє сповіщення в реєстрі. Цикл, який спершу підтверджує, а обробляє другим
кроком, **втрачає кожне сповіщення, обробка якого зазнала невдачі**: запит на трансфер, на який ви
вже не можете відповісти, результат create в очікуванні, який ви вже не можете звірити, — і не
лишається ні того, з чого повторити, ні запису про те, що щось загублено. Реєстр не може надіслати
його знову, і немає жодного сліду того, що зникло.

Отже: **якщо ваш обробник відхиляє проміс, сповіщення не підтверджується.** Воно лишається в
голові черги, а відмова доходить до вас. Усуньте причину, спорожніть чергу знову — і нічого не
втрачено. Наслідок цього навмисний: обробник, який завжди зазнає невдачі, бачить те саме
сповіщення на кожному спорожненні, бо альтернатива — викинути його.

```js
try {
  await client.poll.drain(async (notice) => {
    await store(notice);           // якщо це кине виняток, сповіщення лишиться в черзі
  });
} catch (err) {
  // Черга ціла. Сповістіть, виправте, спорожніть знову.
}
```

### Доставлення щонайменше один раз

Якщо невдачею завершується саме підтвердження — з'єднання обривається між розв'язанням вашого
обробника й доставкою `ack` — сповіщення все ще в черзі, і наступне спорожнення віддасть його вам
знову. Зробіть обробник ідемпотентним і усувайте дублікати за `messageId()`, власним
ідентифікатором цього сповіщення в реєстрі:

```js
await client.poll.drain(async (notice) => {
  const id = notice.messageId();
  if (await alreadyProcessed(id)) return;    // повторне доставлення, а не нова подія
  await store(id, notice.queueMessage(), notice.pendingActionData());
});
```

### Що зупиняє цикл

Спорожнення завершує лише `1300`. Порожність ніколи не виводиться з того, що «у відповіді не було
сповіщення», бо відмова — закрита сесія, призупинений обліковий запис — виглядає з цього боку
точнісінько як спорожнена черга, і цикл повідомив би про успіх, тоді як нічого не було прочитано.
Будь-яка інша відповідь без сповіщення кидається як `CommandError`, побудований з її власного коду
відповіді, тож сесія, якої вже немає, доходить до вас як помилка сесії, а не як нуль оброблених.

## Що несуть сповіщення

Крім тексту, більшість сповіщень несе структуроване корисне навантаження в `<resData>`, і ті самі
методи доступу, що читають відповідь `info`, читають його й тут.

| Сповіщення | Навантаження | Чим читати |
|---|---|---|
| Трансфер запитано / підтверджено / відхилено / скасовано | `trnData` | `transfer()`, `transferStatus()`, `objectName()` |
| Домен зареєстровано, продовжено, видалено, відновлено | `infData` | `objectName()`, `expiryDate()`, `statuses()`, `rgpStatus()` |
| Результат відкладеної (`1001`) операції | `panData` | `pendingActionData()` |
| Низький баланс | `balance:infData` | `balance()`, `currentBalance()` |

### Сповіщення про трансфер

Те, на яке треба відповісти, а не підшити. Його отримують обидві сторони; різниця в тому, хто з
вас може діяти.

```js
await client.poll.drain(async (notice) => {
  const t = notice.transfer();
  if (!t) return;

  // { status: 'pending', requestedBy: 'DELTA', requestedAt: '...',
  //   actingClient: 'EXAMPLE', actBy: '2026-08-21T09:15:00Z', expiryDate: '...' }
  if (t.status === 'pending' && t.actingClient === myClid) {
    // actBy — це строк, і мовчання завершує трансфер: після нього реєстр
    // ПІДТВЕРДЖУЄ запит, а не скасовує його.
    await queueForOperatorDecision(notice.objectName(), t.actBy);
  }
});
```

### Сповіщення про відкладену дію

Саме так відкладена команда звітує про себе. Ви надсилаєте create, отримуєте `1001` («прийнято;
результат буде далі») зі `svTRID`, а відповідь надходить сюди пізніше.

```js
const p = notice.pendingActionData();
// { object: 'example.com.ua', success: true,
//   clTRID: 'EXAMPLE-20260816091500-1234-0007',
//   svTRID: 'SRV-20260816091500-24191-00042',
//   date: '2026-08-16T09:20:00Z' }
```

Два поля визначають усе, що ви з ним робите:

- **`success`** — єдине, що каже, чи операція спрацювала. Обгортковий `1301` означає «ось
  повідомлення», а не «ваша операція вдалася»; якщо читати замість нього код відповіді, кожна
  poll-відповідь виглядатиме успіхом. Відсутній вердикт — це не вердикт: усе, крім явного «так»,
  повертається як `false`.
- **`svTRID`** — це ідентифікатор **початкової** команди, а не цього poll. Зіставте його з тим,
  який ви зберегли, коли отримали `1001`, щоб знати, якої операції в очікуванні стосується
  сповіщення. Черга — це не стек: не припускайте, що йдеться про найсвіжішу.

### Сповіщення про низький баланс

Той самий елемент, який повертає [запит балансу](balance.md), тож один парсер обслуговує обидва
випадки:

```js
const b = notice.balance();
if (b) {
  // { creditLimit: '0.00', balance: '120.00', availableCredit: '120.00' }
  // Гроші — це точний десятковий РЯДОК. Ніколи не розбирайте його у float перед порівнянням.
}
```

Реагуйте на нього. Щойно кошти вичерпано, платні команди відхиляються з `2104`, і реєстрація, яку
ви збиралися зробити, зривається через брак коштів, а не через щось хибне в самому запиті.

### Зміна, яку реєстр зробив з вашим об'єктом (RFC 8590)

Деякі сповіщення описують те, що сталося з вашим об'єктом без вашої команди: він перестав існувати
в реєстрі або пішов трансфером. Саме на них треба реагувати автоматично — припинити тарифікацію,
повідомити клієнта, прибрати зі свого обліку, — а речення в `<msg>` написане мовою сповіщень
вашого облікового запису, тож розбирати його ненадійно.

```js
const chg = notice.change();
if (chg) {
  chg.operation;       // 'delete' | 'transfer' | 'renew' | 'update' | 'restore' | 'autoRenew' | …
  chg.state;           // 'before' | 'after'
  chg.who;             // 'Registry'
  chg.date;
  chg.svTRID;
  chg.reason;
  notice.objectName();
}
```

**`state` каже, як читати об'єкт поруч.** `after` описує об'єкт таким, яким він є зараз.
`before` — таким, яким він був востаннє; для домену, якого вже немає, інакше й не опишеш. Записати
блок `before` у власне сховище як *поточний* стан — це саме те, як вилучений домен оживає у ваших
записах, тож розгалужуйтесь за цим полем перед збереженням.

`change()` не повертає нічого, коли сповіщення не несе блоку зміни, — а це кожне сповіщення, якщо
ви не оголосили `urn:ietf:params:xml:ns:changePoll-1.0` під час входу. Ця бібліотека віддзеркалює
greeting сервера в `<svcs>`, тож реєстр, який його пропонує, оголошується за вас.

На відміну від правила про переміщення, відсутність оголошень **не** дає вам `changeData`: реєстр
надсилає його лише клієнту, який назвав простір імен, бо клієнт, що ніколи його не бачив, може
відкинути весь кадр. Речення `<msg>` не змінюється в обох випадках, тож оголошення ніколи не
забирає того, що ви вже читаєте.

## Коли навантаження надходить переміщеним (RFC 9038)

Сповіщення записується у вашу чергу ще до того, як реєстр знає, яка сесія його забере, тому воно
може містити елемент із простору імен розширення. Якщо ваш вхід оголосив перелік розширень і цього
простору імен серед них не було, реєстр не кладе елемент у `<resData>`, а переносить його в
`<extValue>` усередині `<result>` разом із причиною, яка називає простір імен, що його треба було б
оголосити.

За замовчуванням ця бібліотека входить, оголошуючи рівно ті розширення, які запропонувало
привітання сервера, тож ви отримуєте типізовану форму. Переміщену форму ви побачите, лише якщо
звузите `extUris` у [конфігурації](session.md).

У будь-якому разі кадр лишається валідним, дані лишаються в ньому, а сповіщення лишається
підтверджуваним — нічого не відкидається мовчки:

```js
for (const ext of notice.extValues()) {
  ext.element;     // 'infData'
  ext.namespace;   // URI, який не було оголошено
  ext.values;      // нащадки за іменем: { balance: '120.00' }
  ext.xml;         // елемент у тому вигляді, як він надійшов, щоб розібрати його самостійно
  ext.reason;      // чому його переміщено
}
```

Завжди виконуйте `ack` для такого сповіщення, як і для будь-якого іншого. Якщо лишити його через
незвичний вигляд, черга за ним застрягне.

## Повне спорожнення черги, від початку до кінця

```js
const { Client, Config, EppError } = require('@epptools/sdk');

const client = new Client(new Config({
  host: 'epp.registry.example',
  clid: 'EXAMPLE',
  password: 'your-secret',
  caFile: '/path/to/registry-ca.pem',
}));

try {
  await client.connect();
  await client.login();

  const processed = await client.poll.drain(async (notice) => {
    const id = notice.messageId();
    if (await alreadyProcessed(id)) return;

    await store({
      id,
      queuedAt: notice.queueDate(),          // власний рядок реєстру
      text: notice.queueMessage(),
      lang: notice.queueMessageLang(),
      object: notice.objectName(),
      transfer: notice.transfer(),
      pending: notice.pendingActionData(),
    });
  });

  console.log(`${processed} notices processed`);
  await client.logout();
} catch (err) {
  if (err instanceof EppError) console.error(err.message);
} finally {
  client.disconnect();
}
```
